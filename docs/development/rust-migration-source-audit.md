## 1. Audit boundary and repository size

The recursive Git tree for the recorded `main` baseline contains 219 entries, including:

- **80 Python source files** under `crucible/`, approximately **1.70 MB** of source text.
- **62 Python test/support files** under `tests/`, approximately **755 KB** of source text.
- Eleven Python package directories/subpackages.

These counts describe source-control contents, not installed package size or runtime memory. They are not a performance benchmark. The migration PR adds two Python parity tests under `tests/` (`test_rust_pack_version_fixtures.py` and `test_rust_pack_identity_fixtures.py`), so the current PR branch contains 64 Python test/support files.

The repository is a layered desktop application, not a narrow launcher. Important ownership boundaries are:

- CLI dispatch and user-facing command behavior: `crucible/__main__.py`.
- Persistent server identities and model behavior: `crucible/data/`.
- Host/process observations and tmux lifecycle operations: `crucible/process/`.
- External package formats and provider integrations: `crucible/importers/`, `crucible/exporters/`, and `crucible/mods/`.

- Qt presentation, user decisions, and background worker coordination: `crucible/ui/`.
- Diagnostic parsing and optional repair: `crucible/diagnostics/`.

No runtime implementation was changed during this audit.

## 2. Module map

### 2.1 CLI and application entry

`crucible/__main__.py` is about 2,024 lines and combines argument parsing, command handlers, GUI startup dispatch, shortcut actions, pack maintenance, backups, and recovery commands. Shared behavior is mostly delegated to domain/process modules, but this file is still a large integration surface.

Important CLI families observed:

- Registry and inspection: list, add, remove, scan, info, edit, validate, doctor.
- Lifecycle: start, stop, restart, status, attach, send, shortcut action.
- Import/install: Prism scan/import, mod downloads, modpack/server installation, version discovery.
- Safety/maintenance: property repair, loading diagnostics, backup-fleet run/list/verify, pack update, rollback, previous-install pruning.
- GUI launch: imported only after the selected command dispatches to GUI mode.

Top-level imports include the instance manager/model, world-start inspection, crash heartbeat, tmux manager, and common CLI formatting. Several heavier import/installer/diagnostics modules are imported inside the relevant handler. The Qt GUI imports PyQt and the UI package only in `cmd_gui`; CLI commands do not initialize Qt. However, after argparse has selected a valid command, `main()` always constructs and loads `InstanceManager` and constructs `TmuxManager` before dispatch, including for standalone archive probes and version-list requests. `--help` exits in argparse before that work; no-argument invocation prints the banner/help and exits successfully before loading the registry. This is a measurable CLI startup/import boundary, not currently a benchmark result.

The actual `argparse` tree currently registers 32 subcommands (the leading file docstring is only a short, older subset). The command names are:

`gui`, `list`, `check-updates`, `update`, `rollback`, `prune-previous`, `probe-pack`, `add`, `remove`, `start`, `fix-properties`, `fix-loading`, `stop`, `shortcut-action` (hidden), `restart`, `status`, `attach`, `send`, `scan`, `scan-prism`, `import-prism`, `create-server`, `install-modpack`, `list-mc-versions`, `install-server`, `download-mods`, `accept-eula`, `doctor`, `validate`, `backup-fleet`, `info`, and `edit`.

Notable option contracts include explicit `stop --force` for no-save process termination, graceful `stop --timeout` and `restart --timeout`, `update --dry-run`/prerelease/downgrade/source/variant/preserve-previous choices, `rollback --keep-current-world`, `import-prism --overwrite`/EULA/download/install flags, and mutually exclusive fleet backup `--list`, deep `--verify`, `--install-timer`, and `--remove-timer` modes. `shortcut-action` accepts only start/stop and an instance ID; it is hidden from normal help and deliberately has graceful-stop-only behavior in its dispatcher.

Preserve that lazy import behavior if the package is reorganized. The model and registry types are strong candidates for stable cross-language contracts, but they must not be redesigned solely to look more idiomatic in Rust.



### 2.2.1 The instance model is a mixed domain/filesystem object

`ServerInstance` is not a pure data-transfer object. Its stable core is the registry identity and metadata contract:

- `id`, `path`, `name`, `version`, `pack_source`, Minecraft/loader versions, launch args, tmux session, watchdog preference, created/last-started timestamps, FML prompt choice, and `extra` unknown fields.
- `to_dict()` and `from_dict()` preserve forward-compatible unknown registry keys through `extra`, normalize invalid FML prompt values to the safe `ask` default, and retain legacy defaults for missing fields.
- `_derive_session_name()`, memory token parsing/rewriting, loader/version normalization helpers, and TPS command selection are candidates for pure domain functions once fixture behavior is frozen.

The same class also performs filesystem and host queries: validate paths, find launch scripts/logs, count/read mods, inspect world directories, read `server.properties`, inspect EULA, search launcher files, discover Java, and compute world sizes. `set_eula_accepted()` writes a file; `set_memory_mb()` only updates the in-memory Java argument string until the caller persists the model.

This is a key migration boundary: do not port the whole `ServerInstance` class as if it were a clean Rust struct. Separate (a) the versioned registry/domain record, (b) pure parsing/classification helpers, and (c) filesystem/process adapters. The public Python object can continue to be the compatibility facade while these components are gradually extracted.

### 2.2.2 Registry serialization, identity, and heartbeat path contracts

The registry and heartbeat store are separate persistence adapters. Their current behavior is not equivalent to a typed/schema-validating record store.

**Registry load and model behavior**
- The on-disk schema constant is `REGISTRY_VERSION = 1`, with a 16 MiB load cap. `load()` requires the root to be a JSON object and `instances` (if present) to be a list, but it does not require or validate the root `version` field. It also ignores unknown root keys.
- Every record is passed to `ServerInstance.from_dict()`. It requires `path` and `name`, but does not validate the JSON types/ranges of other known fields or validate `id`/existing `tmux_session` format. Missing `id` generates a new UUID in memory on each load; it is not written until a later save. Missing/empty `tmux_session` is derived from the display name. `validate_session_name()` is applied on `add_instance()`, not on records loaded from disk.
- Per-record unknown keys are preserved in `ServerInstance.extra`; `to_dict()` writes them first and known fields second. This protects newer per-instance metadata from an older build. Unknown **root-level** registry keys are not retained: `_write_instances()` always writes only `version` and `instances`. A registry claiming a future version can therefore be loaded as version 1 semantics and silently rewritten/downgraded on save.
- Registry paths are expanded and resolved during load, even if the server directory is currently missing. This produces a normalized absolute path and follows existing symlinks; it is not a stable path string if the symlink target changes between runs. Duplicate normalized paths, duplicate IDs and duplicate tmux session names are rejected.
- External-change detection compares `(st_dev, st_ino, st_size, st_mtime_ns)`; it does not hash the content. The one supported reconciliation is limited to `last_started` and `last_started_world`, preserving the existing in-memory `ServerInstance` objects. A concurrent edit outside that narrow diff leaves writes disabled until restart.

**Two-process coordination and persistence authority**
- The normal product intentionally has separate `InstanceManager` objects in the GUI and CLI. The one supported cross-process edit is a narrow reconciliation of `last_started` and `last_started_world`; any other detected change disables writes in that process until restart. This is a useful conflict guard, but not a transaction lock.
- The current signature is `(st_dev, st_ino, st_size, st_mtime_ns)`. It follows a registry symlink and omits `st_ctime_ns` and a content digest. If content is rewritten while preserving inode, size and mtime, the signature can remain equal even though the JSON changed. The check is also separate from the later temp write and replace.
- Two processes can both observe the same known signature, both pass `registry_changed_externally()`, and then race. The deterministic `instances.tmp` name means they can truncate/write the same temp inode or replace each other's temp path. Even if both writes complete, each snapshot is derived from that process's stale in-memory list; the final replace can lose the other process's addition/removal or configuration change. The narrow lifecycle reconciliation only runs at selected GUI checks and does not serialize arbitrary CRUD writes.
- The config directory is created with default umask-derived permissions and is not explicitly chmod-restricted or checked for symlink components. `instances.json` load/read follows a symlink; the registry writer's final `Path.replace()` replaces the leaf entry but does not validate the parent directory chain.
- There is no focused multi-process test using two separate `InstanceManager` objects and synchronized writes. The current tests verify a single manager's external-edit detection and disk-first in-memory commit behavior; they do not prove there is no lost update between two cooperating Crucible processes.

**Cross-feature instance-ID storage map**
| Consumer | How it uses the ID | Current safety/compatibility |
|---|---|---|
| Registry JSON | Stores the raw ID as a record field and compares it for lookup/duplicate detection | No type/format/path-segment validation on records loaded from disk; normal new objects default to UUIDs but the model accepts caller-supplied strings |
| HeartbeatStore | `<id>.json` filename under `state/heartbeats/` | Raw ID is interpolated directly into the path; this is an unsafe path-component boundary |
| Legacy BackupManager | Per-instance directory `~/.local/share/crucible-backups/<id>/` | Constructor interpolates raw ID directly and does not apply the safer helper used by fleet migration |
| FleetBackupManager generation layout | `_server_key(id)` SHA-256 hex directory under `generations/<generation>/servers/` | ID is hashed before filesystem use; no raw-ID path traversal through the generation tree |
| FleetBackupManager legacy archive lookup | `_legacy_backup_dir(instance)` | Explicitly rejects empty, dot/dot-dot, path separators and IDs whose basename differs; accepts historic non-UUID leaf strings |
| Custom server icon | `sha256(id).png` under Crucible's icon store | ID is hashed before filename construction |
| In-server `.crucible/` metadata | Fixed filenames under the registered server root | Uses the resolved server path, not the ID as a path segment |

The system should have one central identity/path-component policy, but changing the ID is not equivalent to changing a display name. Existing safe non-UUID IDs are valid compatibility data (tests and direct callers use values like `inst-1`, `Main-id`, and `id-1`). A safe portable component rule should reject empty/dot/dot-dot, slash/backslash, absolute/drive prefixes, NUL/control characters and platform-reserved trailing dot/space cases, while retaining ordinary alphanumeric/dot/underscore/hyphen historic IDs. Do not silently replace an unsafe persisted ID with a new UUID on each load or automatically rename only some of its sidecars. Load it as an explicit invalid-identity state and provide a reviewed migration that inventories/validates its heartbeat and legacy backup data, records the old-to-new mapping, and updates every dependent path in one recoverable operation. The two direct raw-ID consumers must validate independently even if the registry already performs validation, because they are public adapter boundaries.
**Heartbeat read/modify/write coordination**
- `HeartbeatStore._write()` uses a random `mkstemp` in the state directory, so the temporary file itself is exclusively created and does not reuse a predictable path. It flushes/fsyncs the file before `os.replace()`. This is stronger temp-name handling than the registry writer, but it still does not fsync the state directory after replacement. The state directory and its ancestors are created with default umask-derived permissions; the code does not explicitly reject symlinked state-directory components or enforce a 0700 owner-private directory. The final per-ID file is atomically replaced rather than followed, but a symlinked parent directory redirects both temp creation and publication.
- `mark_stop_requested()`, `mark_stopped_clean()`, and `mark_crashed_handled()` each read the current JSON and then write a merged payload in a separate operation. There is no per-instance `flock`, generation number, compare-and-swap, or version recheck around the read-modify-write. A GUI and CLI operation can overwrite a newer state transition with a stale merge. In particular, a delayed `stop_requested` write can race a successful `stopped_clean` write, or startup reconciliation can mark a heartbeat handled after another process has recorded a fresh running state.
- `mark_running()` replaces the entire record with its four current fields. This is intended for a newly confirmed running transition, but it can erase any unknown future heartbeat fields written by a newer build. The read/transition methods accept any JSON object without validating the state enum, boot ID, session name, or timestamp.
- `read()` reads an unbounded file, follows symlinks and returns `None` for missing, malformed JSON, or non-object content. It catches `OSError` and `JSONDecodeError` but not `UnicodeDecodeError`: invalid UTF-8 can escape `HeartbeatStore.read()` and abort startup reconciliation rather than producing an unavailable result. For caught failures, reconciliation treats corrupt/unreadable heartbeat data the same as no prior heartbeat and silently skips a crash report. This is fail-safe against false positives, but hides state uncertainty; a better adapter should preserve `Missing`, `Valid`, and `Invalid/Unavailable` distinctly for diagnostics without ever turning invalid into a crash claim.
- The instance ID is used as the final filename component and is not validated by `ServerInstance.from_dict()`. The store should independently validate one safe filename component before read/write; do not require UUID-only IDs without checking compatibility with historic IDs.

**Registry publication caveats**
- `_write_instances()` uses a deterministic sibling path, `instances.tmp`, opens it with ordinary text `open("w")`, flushes/fsyncs the file and calls `Path.replace()`. It does not use `mkstemp`/exclusive creation/no-follow semantics for that sibling; a pre-existing `instances.tmp` symlink can be followed/truncated when the writer opens it.
- It does not fsync the containing config directory after replace. The rename is atomic for ordinary readers, but the method's “durably publish” wording is stronger than the source proves for sudden power loss because the directory entry is not explicitly flushed.
- The signature check and fixed temp write have no inter-process lock. Two Crucible processes that pass the external-signature check before either publishes can race on the same temp name or overwrite one another's complete registry snapshots. Current tests cover failed add/remove memory state and external-edit detection/reconciliation, not concurrent two-writer races, temp symlink, root schema version, unknown root keys or directory-fsync failure.
- `validate_delete_target()` rejects a leaf symlink, broad targets, and mount points before recursive deletion. This remains a separate delete guard, not a property of the registry path itself.

**Heartbeat identity path**
- `HeartbeatStore._path(instance_id)` appends the raw registry ID to a filename. `ServerInstance.from_dict()` and `InstanceManager.load()` do not currently restrict IDs to a single safe path component. A malformed/hand-edited ID containing `/`, `..`, or an absolute path can escape the heartbeat directory; `HeartbeatStore._write()` then uses `os.replace()` to publish the generated JSON at that derived destination. This is a source-level path-construction issue, not an observed exploit. Add a safe ID-segment validator at the registry boundary and retain support for existing safe IDs such as the test IDs `inst-1`; do not assume every historic ID is a UUID.
- `HeartbeatStore.read()` has no file-size cap or field/schema validation. Missing file, malformed JSON, and non-object JSON all become `None`; `reconcile()` skips all three as if there were no usable heartbeat. That avoids false crash reports, but it also hides corrupt-state uncertainty from the owner.
- Heartbeat writes use a random `mkstemp` in the state directory, flush/fsync the file and atomically `os.replace()` it. Like the registry writer, it does not fsync the parent directory. The unique temp file is better protected against collision/symlink attacks than `instances.tmp`, but the final destination still comes from the unvalidated ID.

**Rust/data-model boundary:** preserve unknown record fields and current defaults only after schema version is explicitly understood. The first typed API should represent `RegistryLoad::Missing`, `Loaded(version, records, unknown_root)`, and `Invalid/Unsupported(reason)`, rather than interpreting unsupported schema as version 1. Keep path resolution and atomic publication in Python. Before production serialization moves, add a schema-version migration policy, safe identifier validation, no-follow/exclusive temp publication, directory fsync, and two-process lost-update tests.

**Additional path-identity and call-site findings**
- `InstanceManager.add_instance()` calls `Path(path).expanduser().resolve()` before creating the record. `load()` does the same for persisted paths. The record stores the resolved target, not the original path string or whether the user selected a symlink alias.
- The GUI's permanent-delete path calls `validate_delete_target(instance.path)`, which refuses a leaf symlink. But because the registry path was already canonicalized, a server folder originally added through a symlink alias is now represented as the real target path. The delete guard cannot distinguish that original alias; it will accept the canonical directory and the UI will rename it to a quarantine sibling then recursively delete it. The confirmation shows the resolved target, which is better than deleting the symlink itself, but the documented "reject symlink" rule only applies to a symlink still present at delete time. The code has no explicit "registered through symlink" provenance or policy. Treat this as a path-identity decision, not an established vulnerability: decide whether registration should reject symlinked roots, preserve the user's original spelling plus canonical target, or explicitly disclose canonical-target deletion. Add a registration-through-symlink test so any Rust representation cannot accidentally change the meaning.
- `find_server_dirs()` is the CLI `crucible scan` implementation. It resolves the search root, lists each directory's children, and uses `child.is_dir()` without checking `is_symlink()`. It therefore follows directory symlinks during recursion, can scan outside the requested tree, and can visit the same physical directory through multiple aliases. The depth limit prevents unbounded recursion through a cycle but does not make traversal stay beneath the root or prevent duplicate visits. It catches `PermissionError` from `iterdir()` only; other `OSError` can escape the scan.
- The scan command is read-only: it prints candidates and tells the owner to run `crucible add <path>`; actual registration then resolves the displayed path again. Thus a symlink found during scan is likely displayed under its alias but stored under its resolved target. There are no dedicated tests in `test_core.py` for `find_server_dirs()`, symlink traversal, outside-root discovery, or duplicate physical directory visits.
- The normal MainWindow startup path invokes heartbeat reconciliation after loading the registry. Since registry IDs are currently accepted from JSON without path-segment validation and HeartbeatStore uses the raw ID as a filename, this is not just an unused helper: an unsafe ID can reach heartbeat reads and, after crash classification, a heartbeat write during startup. Keep the ID validator at the registry/HeartbeatStore boundary rather than trusting each call site.




### 2.2.3 Pack provenance, import summary, and owner-added-mod metadata

These three small JSON sidecars drive pack identity and the owner-mod carry-forward decision. They currently have different and mostly best-effort persistence semantics.

**Pack provenance (`.crucible/pack-provenance.json`)**
- `read_receipt()` follows the path with `read_text()` and has no file-size limit, symlink rejection, JSON shape/schema validation, or per-field validation. It returns `{}` only when JSON decoding/read fails or the root isn't an object.
- `identify_pack()` gives the receipt highest precedence. Any truthy `provider` and `version` are cast to strings and treated as authoritative; an absent/unknown `variant` silently becomes the Java 17 default. There is no receipt schema version, checksum, signature, validation of provider/version syntax, or consistency check against the server tree.
- `pack_baseline()` accepts any list under `pack_mods` and converts each member to `str`. There is no filename/path validation, no duplicate rejection, and no distinction between `.jar` and arbitrary names. `compute_carry_mods()` then uses that set as exact evidence of pack-owned files; a forged/stale receipt can change which mods are carried into a future server update.
- `_write_receipt()` enumerates the live `mods/` directory and treats every regular-looking `*.jar` not in `carried` as pack-owned. `Path.is_file()` follows symlinks; there is no symlink rejection or stable hash/identity capture for each JAR. The receipt stores filenames, not the SHA-256 of the bytes used for the baseline.
- Publication uses a fixed `pack-provenance.json.tmp`, ordinary `write_text()`, then replace. It does not use exclusive temp creation, fsync the file/directory, reject a symlink at the final receipt path, or surface failure: `OSError` is swallowed. After a successful live pack swap the update can therefore report success with no new provenance, and future update planning silently falls back to weaker heuristics.

**Import summary (`.crucible/import-summary.json`)**
- `prism.import_prism_source()` writes a rich object (`source`, install root, detected game root and temporary flag, detected metadata, copied counts, optional download result and server-install result) with a direct `write_text()`. There is no atomic temp publication, fsync, size bound, symlink check, schema version or required-field validation.
- `identify_pack()` reads this file without a size cap or symlink check, trusts `source` and `detected.name` as candidate filenames, and only later runs the GTNH name regex. This is an advisory identity source, lower precedence than provenance but higher than the registry/folder heuristic.
- The `detected_game_root` may have been a deleted temporary extraction path; the `detected_game_root_was_temporary` flag explains that. Do not mistake it for the installed server root. A failed write of this summary currently escapes `import_prism_source()` and can make an otherwise mostly completed direct-copy import report failure after many files have already been written.

**Owner-added mod record (`.crucible/added-mods.json`)**
- `modrinth._load_record()` has no size cap, symlink check, schema version, filename validation or record-field validation. A malformed/unreadable file becomes `{}`. It filters the root object to string keys and object values only.
- `modrinth._save_record()` writes a fixed `added-mods.tmp` via ordinary `write_text()` and replace, catches and ignores `OSError`, and has no file/directory fsync. `install_files()` can therefore report per-file successes while the owner-added identity record fails to persist.
- `versions._write_record()` is stronger: randomized `mkstemp` in the same directory, file fsync and `os.replace()`, but no directory fsync, no symlink check on the record path, no schema/size policy, and the caller still does not acquire the fleet operation lock.
- Both `identify_files()` and install/update paths treat the record as advisory provenance. It is not proof that a JAR's bytes still match the stored metadata: `check_update()` looks up project/version metadata, and later `replace_files()` has a stronger SHA-1 verification path for the selected current file.

**Other owner-local sidecars**
- `server_icons.py` hashes the instance ID before using it as a filename, caps image input at 20 MiB and 4096×4096, uses a Crucible-owned private 0700 icon directory, a randomized temp file and 0600 published PNG. This avoids the raw heartbeat-ID path issue for icon storage. It still uses path checks followed by later opens (so source image/root replacement races are not eliminated) and does not fsync the icon directory.
- `sharing/history.py` is the most explicit sidecar schema in this group: version 1, exact event allowlist, 50-record/1 MiB caps, URL/hash/type validation, private 0700 parent/0600 file, randomized temp, file fsync and atomic replace. It deliberately stores no credentials or raw HTTP responses. It does not fsync the parent directory and its check-then-open path handling is not a directory-descriptor sandbox.
- The Crucible import report `CRUCIBLE_IMPORT.md` is human-readable, direct-written and has no schema/security contract; it is not used as authority for automated pack decisions.

**Required Rust/data contract:** don't model “JSON parses” as “trusted provenance”. Define explicit versioned schemas for pack provenance and owner-added records, validate every filename as one safe leaf, reject unknown provider/variant/value types, and bind pack-owned mod baselines to content hashes if they are used for future destructive/carry decisions. The Python adapter must own bounded no-follow reads and durable sidecar publication. For legacy unversioned receipts, add a compatibility reader that distinguishes `LegacyUnverified` from a new `Verified` receipt; do not silently grant an old file the same authority as a newly validated one. Keep import summaries advisory only.

### 2.3 Process and host adapters

- `resource_monitor.py`: Linux procfs process discovery, RSS/CPU sampling, PID association.
- `machine_resources.py`: aggregate host/server usage and optional NVIDIA query.

### 2.3.1 Process matching semantics and a destructive-removal edge

The two existing PID matchers share a broad shape, but their precise semantics must be captured before a consolidation:

- Both prefer the exact `-Dcrucible.session=<session>` token in the process command line. **That marker branch does not check `/proc/<pid>/comm` first.**
- The legacy fallback checks that kernel-reported `comm` is exactly `java`, then matches the registered server path in argv or exact process cwd.
- `machine_resources._instance_processes()` uses sets of session markers and paths and scans `/proc` once for the whole fleet, but it returns only a sorted aggregate PID list, not per-instance associations.
- `ResourceSampler.find_instance_pids()` scans `/proc` independently for each server and returns that server's PID list.

`TmuxManager.start()` constructs `CRUCIBLE_JAVA_ARGS` containing the session marker inside a `bash -c` command. The resource tests currently prove matching for a synthetic Java command line, and prove that a Dolphin/cat command whose *path* happens to contain `java` is not mistaken for a JVM. They do not establish whether a launcher shell that retains the `bash -c` command text can itself match the marker token. Add a representative wrapper-plus-JVM fixture before changing this matcher. If wrappers do match, the team must decide whether to preserve wrapper attribution deliberately or restrict server-PID/resource attribution to the Java executable; do not silently change current behavior in a Rust rewrite.

**Separate high-priority safety observation - removal when tmux is unavailable:** `TmuxManager.safe_to_remove()` currently returns `(True, ...)` immediately when `tmux_available()` is false, without checking `_unmanaged_pids()`. The GUI's `_on_remove_requested()` calls this preflight before offering both Remove from list and Delete server files. Therefore, a Java server started outside tmux can evade this preflight when the tmux executable is missing, and the subsequent Delete server files flow may rename and recursively remove its live server directory. This is distinct from Rust migration and should receive a separate narrowly scoped safety fix plus regression tests: with tmux unavailable and a matching unmanaged JVM present, both unregister and destructive deletion must be blocked; with a complete process scan and no match, behavior can remain safely available. Also test a process-scan-unavailable state - an incomplete `/proc` observation must not be silently treated as an empty process list for destructive decisions.

The current `_unmanaged_pids()` helper catches every exception and returns `[]`; `_iter_pids()` also returns an empty list when `/proc/self/stat` is not visible. That best-effort behavior may be tolerable for a non-authoritative metrics display, but it is not a sound proof of process absence for lifecycle safety. The call sites include `is_server_ready()` (which gates save/backup consistency), `get_status()` and `status_map()` (which can classify an unmanaged live JVM as stopped), `safe_to_remove()` (which gates registry removal and folder deletion), `stop()`/`attach()` (which refuse to control an unmanaged process), and `_force_kill()` (which uses an empty PID list after `tmux kill-session` as proof the JVM died, and again after SIGTERM/SIGKILL as proof escalation succeeded). When process discovery is incomplete, `_force_kill()` can falsely report success while a JVM survives, and status/backup paths can treat an incomplete observation as stopped. A future API should distinguish `complete scan with no match`, `matching PIDs`, and `incomplete/unavailable scan`. Keep metrics best-effort while requiring complete observations for safety actions. For explicit force-kill, report that process exit could not be verified; never declare success from an incomplete scan.


**Additional force-kill safety detail - numeric PID reuse:** after tmux session teardown, _force_kill() obtains integer PIDs from the process scan and sends SIGTERM to those numeric PIDs. It waits one second, performs a fresh scan, then sends SIGKILL to the newly observed PID list, waits another 0.5 seconds, and performs a final scan. The fresh second scan is a useful safeguard; it does not reuse the first list after the wait. However, each individual enumeration-to-os.kill() interval still has a PID reuse race: a matched process can exit and the kernel can assign its PID to another process before the signal is delivered. In the multi-PID case, that interval also exists for later entries in the already-collected list. A force-kill must never signal a process merely because its PID was once associated with the server.

A stable process handle is a candidate for the safety fix. Linux pidfds are designed to avoid this PID-reuse race: pidfd_send_signal() addresses the process referred to by a file descriptor and returns ESRCH if that process has exited, rather than signaling an unrelated process that inherited the numeric PID. Python's current minimum (3.11) exposes os.pidfd_open() on Linux >=5.3 and signal.pidfd_send_signal() on Linux >=5.1; see the [Python 3.11 os documentation](https://docs.python.org/3.11/library/os.html), [Python 3.11 signal documentation](https://docs.python.org/3.11/library/signal.html), and [Linux pidfd_send_signal manual](https://www.man7.org/linux/man-pages/man2/pidfd_send_signal.2.html). A safe implementation still needs to bind the opened pidfd to the same observed process identity before signaling, hold the descriptor through both escalation steps, and close it on every path. If pidfd support is unavailable or process identity cannot be confirmed, fail closed and report that force-kill could not be safely completed; do not silently fall back to a stale bare PID across delays. Test exit-before-signal, PID reuse simulation, multiple matched processes, EPERM/ESRCH, and descriptor cleanup.


**Separate high-priority safety observation - launch when a server is already running outside tmux:** the same incomplete process-discovery contract affects Start, not only removal. TmuxManager.start() does not call _unmanaged_pids() or require a complete process scan. Its current guards are: tmux must be installed; the exact configured tmux session must not be positively running (via the boolean is_running() wrapper); a start script must exist; and _port_conflict_message() checks whether an IPv4 listener overlaps the port/address currently read from this instance's server.properties. That last check is useful, but it is not proof that no matching Java server process exists: it only examines the configured IPv4 bind/port and may not identify a process that is still starting, uses an unparsed bind address, or has a different effective bind than the registry/config expects.

The launch callers do not all add a fresh, identity-aware process check:
- CLI cmd_start() performs world inspection and property preflight, then calls tmux.start() directly; it does not call get_status() first.
- GUI InstancePanel._begin_start_after_world_check() relies on the cached _current_status == "stopped" value, then calls tmux.start(). The UI status came from the periodic health path and can be stale; it is not a process-absence proof at the final action boundary.
- Hidden desktop shortcut-action start obtains a fresh get_status() and only continues for stopped, but that still inherits the best-effort _unmanaged_pids() behavior that collapses errors to an empty list.
- Watchdog._do_restart() re-inspects world safety and then calls tmux.start() without a process-absence scan. It relies on prior tmux/pane misses and the shared start method.
- CLI cmd_restart() is more defensive: it checks get_status() and rejects any state except running or stopped, but its result still inherits the lossy procfs semantics.

Consequently, a manual Java server outside the registered tmux session can be missed by the CLI, GUI race window, shortcut (when the scan is incomplete), or watchdog restart. The configured-port check may catch common conflicts, but it does not establish process identity/absence. A Start path that proceeds can create a new tmux session and launch a second JVM against the same files. Treat this as a separate high-priority safety prerequisite alongside removal: before a launch, require a complete process observation and block if any PID is associated with this instance; if the scan is incomplete, return Unknown and do not launch. Revalidate at the shared TmuxManager.start() action boundary, not just in individual front ends. Keep the existing port-conflict check as an additional guard, not a substitute.

Existing Start regression coverage is insufficient for this contract. StartTests.test_start_wrapper_has_no_unbounded_tee patches is_running=False and _port_conflict_message=None, then expects launch success; it does not assert any unmanaged-process scan. Watchdog security tests cover the reboot wrapper still owning its tmux session (where TmuxManager.start() sees the session and refuses a competing launch), but not a detached/unmanaged Java process after the session disappears. Add shared-start tests for a matching process, an incomplete procfs scan, tmux session absent plus unmanaged Java, and complete no-match; add caller-level checks for CLI, GUI, shortcut and watchdog dispatch. Do not change this behavior as part of a performance batching or Rust migration patch.



### 2.3.4 Worlds-tab legacy archive inventory is synchronous and repeated on first load

`WorldTab.load()` calls `_refresh()` synchronously and then starts the asynchronous fleet recovery-list worker. The first `_refresh()` performs these operations on the Qt GUI thread:

- `BackupManager.list_backups()` globs every legacy `*.zip`, stats each file and reads its optional sidecar label.
- `FleetBackupManager.list_legacy_world_archives()` loads the newest complete manifest using the fast manifest path and stats/checks each migrated archive.
- For every combined archive entry, `WorldTab._refresh()` calls `BackupManager._backup_level_name(entry)`; this opens the ZIP and materializes its full `namelist()` to identify the root folder. It does not decompress payloads, but central-directory parsing/memory grows with archive member count.
- It then builds all row widgets, scans pre-swap directories and starts the recursive world-size worker. The actual recursive size walk is already off-thread and queued safely when one is in flight.

When the fleet recovery-list worker completes, `_on_recovery_job_finished(mode="list")` updates `_world_recovery_points` and calls `_refresh()` again. That second refresh repeats the legacy ZIP glob/sidecar/stat work and opens every archive central directory again, even though only the recovery-point data changed. This is a source-confirmed duplicate first-load pass; actual UI latency depends on archive count and each ZIP's central-directory size and has not been benchmarked. Existing `test_world_stats_thread_guard.py` verifies that the recursive world-size worker is not replaced while running and that a queued size refresh resumes after completion; it does not instrument `_refresh()`, count `_backup_level_name()` calls, or prove the legacy archive inventory stays off the Qt thread. `test_backup_ui.py` exercises the fleet restore worker directly, not the WorldTab list/render path.

This differs from the standalone Fleet Backups tab: its `BackupTab._refresh()` dispatches the list operation through `_FleetBackupWorker`, which calls `list_generations()`, `generation_issues()`, `legacy_source_inventory()`, and recovery-point listing away from the GUI thread. WorldTab does use a worker for its fleet recovery-point data, but the legacy ZIP inventory around that worker remains synchronous.

Performance-first Python candidates:
1. Split archive discovery/root-name inspection into the existing recovery worker result, so the UI receives one immutable archive metadata snapshot instead of opening every ZIP on each refresh.
2. Reuse the same archive inventory when only `_world_recovery_points` changes; rebuild the table from cached immutable entries.
3. If legacy archives have no safe cached root metadata, key any cache by a verified identity (e.g. stable file signature plus archive digest where already available), never by filename alone.
4. Keep ZIP validation/hash verification before restore; a presentation cache must not authorize restore or replace the deep restore preflight.

Add a Qt test that counts `_backup_level_name()` calls during initial WorldTab load and recovery-list completion, asserts central-directory enumeration does not run on the GUI thread after the refactor, then a benchmark with 0/10/100/500 legacy archives and controlled member counts. Measure first paint, GUI event-loop delay, central-directory bytes/entries and total root-name parsing time. The target is one background inventory per view generation, not a Rust ZIP parser.

### 2.3.3 Resource sampling embedded in the Diagnostics/Info page

The resource sampler is dependency-free and reads Linux procfs directly:
- _iter_pids() first checks whether /proc/self/stat exists and then calls os.listdir('/proc') to build the full numeric PID list. The os.listdir() call is not inside a try/except, so an inaccessible or transiently failing procfs enumeration can raise despite the module-level 'best-effort and never raises' statement.
- ResourceSampler.find_instance_pids(instance) performs a complete process-table walk for one instance. For every PID it reads cmdline; if the exact -Dcrucible.session=<slug> token is absent, it reads comm, and for Java processes may read cwd. The exact marker path accepts a process without first validating its executable name; the legacy path/cwd fallback requires comm == java. This is the same matching contract used by lifecycle detection and must not be changed by a metrics optimization.
- sample_pids() reads /proc/<pid>/stat, statm, and cmdline for each selected PID and computes CPU from the previous sample; it is stateful, so callers should retain a ResourceSampler instance. The first CPU result is zero until a second sample establishes a delta.
- `SystemTab` is not a separate top-level workspace tab. `InfoTab` constructs one persistent `SystemTab` child and inserts it into the Diagnostics/Info page; `InstancePanel._load_current_tab()` only calls `InfoTab.load()`. The child starts a 2-second `QTimer` when shown and stops it on hide. `InfoTab.load()` calls `_system.load(instance)` (which immediately refreshes) and adding/showing the child also runs `showEvent()` (which immediately refreshes); these are two immediate-refresh code paths and their exact event count on first display should be measured in a Qt test rather than assumed. The timer is demand-scoped to the visible Diagnostics page, not a resident hidden System page.
- sample_machine_usage() in machine_resources.py is a separate on-demand path that enumerates managed instances together and waits 350 ms between two samples for CPU; do not assume its aggregate scan is already used by the System tab.

**Diagnostics load also performs duplicated recursive filesystem work on the GUI thread:** `InfoTab.load()` calls `instance.validate()`, and `ServerInstance.validate()` calls `get_bundled_jars()` to enumerate every nested JAR below `mods/`. The same `InfoTab.load()` then calls `get_bundled_jars()` again to display the count/list, repeating that recursive `rglob("*.jar")` traversal. It also calls `get_world_names()` and `get_mod_count()` synchronously, then `SystemTab.load()` performs the full `/proc` process scan and sampling before the new Diagnostics layout is complete. This is source-confirmed duplicate work. A first Python improvement is to compute a bounded immutable diagnostics snapshot once (including bundled JAR paths), reuse it for validation and display, and move the slow/read-only inventory and metrics portions to a generation-checked worker if measurements show a UI delay. Do not use a metrics/process snapshot as a lifecycle safety observation. There is no dedicated InfoTab/SystemTab load-latency test; `test_resource_monitor.py` and `test_machine_resources.py` mock `_iter_pids()` and do not cover this integrated Qt path.

A measured Python-side improvement would be to move the visible-tab sample to a bounded worker and pass back an immutable per-instance observation snapshot, or reuse a shared fresh association scan for metrics. Keep the timer visibility-scoped; never add a global sampler. Explicitly distinguish complete, incomplete and per-PID-disappeared outcomes. Metrics may render unavailable on an incomplete scan, but the same result must not satisfy lifecycle Start/Stop/removal preconditions. A stale metrics snapshot must never be reused by a safety action.
### 2.3.2 Watchdog polling: implementation does not match its batch comment

The module docstring in `watchdog.py` says one `tmux list-sessions` call per poll covers all watched instances. The current `Watchdog._poll()` does not use that operation:

- It reads each watched instance's heartbeat JSON inside the loop.
- For each ordinary `running` heartbeat, it calls `probe_running(instance)`, which launches `tmux has-session -t =<session>`.
- When the session is present, it calls `is_java_foreground(instance)`, which launches `tmux list-panes -t =<session>:`.
- A pending `stop_requested` heartbeat also probes the exact session, and queries the pane while the wrapper remains present.

This is roughly two tmux client subprocesses per watched instance on a normal 10-second poll, not one list-sessions command total. The 10-second timer is demand-driven and stops when no watch or pending Stop remains; do not replace that with an always-running poller.

A batched adapter is plausible: one `list-sessions` observation, followed by one `list-panes -a -F` snapshot when relevant sessions exist. The tmux manual documents `list-panes -a` as listing all panes on the server and `-F` as a format for each line; formats include `session_name`, `window_active`, `pane_index`, `pane_active`, and `pane_current_command` (see https://man.archlinux.org/man/tmux.1.en and https://github.com/tmux/tmux/wiki/Formats). The prototype must map the batch rows to the same active-window/first-pane behavior that the current per-target query returns. Simply taking the first arbitrary pane or the active pane could silently change crash detection. Keep unknown query/format output distinct from Java-not-foreground.

Current tests cover unknown probes, wrapper survival, two-miss confirmation, pending Stop, crash loop limits and world-selection confirmation, but set up one watched instance at a time. There is no multi-instance query-count test, global pane snapshot fixture, or parity test for multiple windows/panes. Add these before changing the watchdog implementation.

### 2.4.1 Archive import routes have different safety and partial-success contracts

**Prism/MultiMC import (`prism.py`, `ui/add_dialog.py`):**
- `_extract_archive()` creates a temporary directory, caps at 100,000 entries, 20 GiB total expanded bytes, 2 GiB per member, and compression ratio 1,000 for members over 100 MiB; archive symlinks and path escapes are skipped with warnings. It streams each entry in 1 MiB chunks, requires the advertised member byte count, and supports placing the temporary directory under a supplied destination parent.
- Important caller mismatch: Prism `_detect_archive(path)` calls `_extract_archive(path)` **without** `dest_parent`, so it expands a potentially multi-GiB import under the system temp directory (often `/tmp`) and later copies the selected files to the chosen server target. `pack_update.apply_update()` instead calls `_extract_archive(arc, staging_parent)`, keeping extraction on the same filesystem as its staging/live rename. The helper docstring explicitly says `dest_parent` avoids tmpfs `/tmp`, but the Prism path does not currently use that feature. This is not just a Rust detail: Prism import of a large server pack can consume tmpfs or require an extra cross-device copy. Before any port, either deliberately preserve this behavior for exact parity or change the Python caller in a separate, tested performance fix that knows the actual destination parent before extraction. Add a regression test asserting the chosen temp root for Prism imports, and a large/sparse generated archive benchmark comparing `/tmp` vs destination-parent placement.
- The returned `PrismImportPlan` retains `cleanup_dir` for archive sources. `import_prism_source()` copies directly into the final target, not a staging/atomic-publish directory. Its normal end-of-function path removes `cleanup_dir`, but the cleanup is not in a `finally`; an `OSError` or unexpected exception during target copy/report creation can leave the extraction directory behind as well as a partially populated target. There are earlier leak points too: `_extract_archive()` removes its temp tree only for `BadZipFile`/`ValueError`; arbitrary `OSError` during member read/write is not cleaned up. `_detect_archive()` calls `_extract_archive()` first and only sets `cleanup_dir` on the plan after metadata parsing; malformed `modrinth.index.json`/`manifest.json` can throw before the temporary path is handed to the caller. Add failure-injection coverage at each point.
- The GUI `AddInstanceDialog` chooses a fresh collision-free target, calls import with `overwrite=False`, and only offers registry registration after the worker reports success. When import fails, it explicitly warns that copied files may remain at the selected target; Cancel after a successful import also leaves the copied files on disk. This partial-folder behavior is a user-visible contract, not something a Rust port should silently turn into recursive deletion.
- `_copy_tree()` recursively copies selected local content with `copy2`, skips client-only path components and symlinks, and verifies each resolved source file remains under the resolved source root. Unlike ZIP extraction, this local-folder copy has no aggregate byte/file-count bound; it can legitimately copy a large installed server pack. Preserve this as a separately bounded/trusted-local-input flow and do not apply archive expansion limits to it without an explicit product change.
- Target handling has a separate symlink edge: `import_prism_source()` calls `Path(target).expanduser().resolve()` before its existing-target/overwrite check. That follows a leaf target symlink, so the later check cannot see that the originally supplied path was a symlink. If the GUI selects a fresh nonexistent target and another process creates a symlink to an empty external directory before the worker starts, the importer resolves it and writes into the symlink destination. The fresh-server and strict Modrinth GUI installers explicitly reject/atomically claim symlink/colliding targets; the Prism importer has no equivalent. Add a raced target-symlink test and use a no-follow parent/leaf claim before writes; do not perform `resolve()` first and assume it validates the original path.

**Modrinth `.mrpack` installer (`modpack_auto.py`, `ui/modpack_dialog.py`):**
- `read_index_from_mrpack()` reads only `modrinth.index.json`, caps it at 16 MiB, validates JSON object shape, and does not extract the archive wholesale.
- `_safe_join()` resolves override paths under the chosen target root. `apply_overrides()` limits member count to Prism's 100,000 cap, individual member to 2 GiB, and total override expansion to 20 GiB; it skips archive symlinks and unsafe paths, streams in 1 MiB chunks, and applies `server-overrides/` after `overrides/` so server-specific files win.
- Unlike `prism._extract_archive()`, this override path does not apply the 1,000:1 compression-ratio check. Individual file-write/extract failures are caught and logged, then the loop continues; `apply_overrides()` returns only the count written. `install_modpack_from_mrpack()` does not convert those skipped/failed files into a structured failure list and ultimately sets `ModpackInstallResult.ok = True` after the stages complete. It can also return `ok=True` when the server-loader install failed, because it continues to lay down mods/config/support files so the owner can finish manually. Here `ok` means a partially or fully laid-out modpack install workflow completed, not necessarily a ready-to-start server with every override and loader succeeded. Keep the nested `ServerInstallResult`, `DownloadResult`, override failures and final readiness distinct in a future typed result. One extra failure hazard: the exception handler calls `dest.unlink(missing_ok=True)` after a write error. In non-strict mode, if `dest` existed before this run, or if a valid `overrides/` copy already created it and the later `server-overrides/` copy fails, this cleanup removes the old/previously-good destination rather than restoring it. Writes are not staged per file and the overwrite is not atomic. Add a test that starts with an existing sentinel file, injects a write failure, and asserts that the old bytes survive; another should fail the server-specific second-pass replacement and assert either the prior general override survives or the failure is surfaced as a destructive partial result, never silently removed.
- GUI strict mode (`target_must_not_exist=True`) checks and then atomically claims the fresh target with `mkdir(exist_ok=False)` after resolving the Modrinth project; the `.mrpack` download is kept under `target/.crucible/source-pack/`. The installer writes directly into that newly claimed target and does not roll back the whole target on cancellation/failure. CLI/direct callers can use non-strict mode and reuse an existing target. Keep these call-site policies separate.

### 2.5.1 Network/provider trust boundaries

Crucible does not have one generic HTTP client today. Its network paths have different policies and should not be consolidated without parity tests:

- `download_http.py` builds a TLS-verifying opener, requires HTTPS without embedded URL credentials, rejects API-key query parameters, strips caller-supplied `x-api-key`, and attaches the user's CurseForge key only to an explicit allowlist of official API/CDN hosts. Its redirect handler rejects cross-host CurseForge redirects rather than forwarding credentials.
- `curseforge.py` retains a provider adapter but hard-disables online integration through `_CURSEFORGE_ONLINE_ENABLED = False`. If re-enabled later, the key must come from the session, environment, or a regular user-owned private key file (mode restricted, no symlink, size-bounded). A Rust port must not silently change this policy.
- `modrinth.py` bounds JSON responses (16 MiB), icon responses (8 MiB), and mod downloads (2 GiB); uses finite request timeouts; resolves exact loader/Minecraft version compatibility; stages downloads to temporary files; and checks a SHA-1 when supplied before replacing the destination.
- `importers/downloader.py` handles indexed pack downloads separately, with cancellation checks, size limits, temporary files, retry/backoff for transient failures, and SHA-512/SHA-1 verification when an expected digest is available. Explicit HTTP denial does not trigger futile alternate-URL retries.
- `importers/serverloader.py` has another installer download path with its own TLS context, finite response/file limits, cancellation and retry behavior, and atomic destination replacement. Do not assume it is behaviorally identical to Modrinth download handling.
- `sharing/gofile.py` has a distinct upload path: it opens the selected ZIP without following symlinks, checks file identity before hashing, validates the SHA-256 against the reviewed artifact, streams from the same file descriptor, and validates the provider's returned URL and metadata. It does not accept an arbitrary URL from the response as a share link, and its optional API token is not persisted or returned.

Migration consequence: any new Rust network adapter must preserve per-provider TLS/root-store behavior, host allowlists, redirect policy, timeouts, body limits, cancellation, retry semantics, hash algorithms, atomic publication and credential redaction. Replacing several Python paths with one convenient HTTP crate is not automatically a correctness-preserving refactor.

### 2.5.2 Existing filesystem mutation owners

The main file-mutating operations are already spread across domain modules and have different rollback contracts:

- Registry publication: `InstanceManager._write_instances()` writes a complete snapshot, flushes/fsyncs the temporary file and atomically replaces `instances.json`; external modification and parse errors block writes.
- Mod inventory changes: `ModManager` controls top-level JAR add/enable/disable/delete; `mods/versions.py` stages compatible files and manages replacement records.
- Server pack update: `importers/pack_update.py` creates a plan first, then stages/downloads/applies the pack while preserving world/config/owner data and retaining rollback/receipt material. GUI and CLI apply callers hold `fleet_operation_lock()` across the mandatory fleet checkpoint and apply; GUI/CLI rollback and previous-install prune callers currently do not hold it.
- Configuration repair: `data/properties.py` validates server properties and saves a backup before repair; `ServerInstance.set_eula_accepted()` writes `eula.txt` atomically.
- Loading repair: `diagnostics/loadcheck.py` separates crash analysis from opt-in JAR quarantine/restore operations.
- World operations: `BackupManager` owns legacy world swap/reset/wipe and pre-swap directories; `FleetBackupManager` owns immutable-generation restore and retention cleanup.
- Import: `prism.py` creates staged target content, import receipts and generated setup files; optional server/mod installation occurs after the core source copy.
- Export/share: `client_export.py` writes a temporary archive then publishes it after verification; `gofile.py` uploads the reviewed artifact without modifying the server folder.

A Rust migration must not create duplicate writers for any of these data classes. For each operation, define one owner, the source/destination paths, preconditions, staging location, publication operation, backup/receipt, failure recovery, and whether cancellation is safe before/after publication. A Rust helper should initially return plans/results or perform a single isolated primitive, not take ownership of whole workflows.

**Global operation-lock coverage is inconsistent and is a separate safety prerequisite:**

`fleet_operation_lock()` is an inter-process, non-blocking `flock(LOCK_EX | LOCK_NB)` on `DEFAULT_FLEET_BACKUP_DIR / fleet-operation.lock`. The current default `DEFAULT_FLEET_BACKUP_DIR` is `~/.local/share/crucible-backups/fleet`, so the actual default file is `~/.local/share/crucible-backups/fleet/fleet-operation.lock`. `FleetBackupManager` also has a separate `fleet-backup.lock` inside this root for generation publishers; this internal publisher lock is distinct from the outer operation lock used to coordinate backups with world/pack effects. Its documented purpose is to serialize fleet backups, pack updates, and destructive world operations so the timer cannot capture an intermediate rename/swap. Importantly, `FleetBackupManager.run_backup()` acquires `fleet_operation_lock(self.root)` itself by default and then takes the separate `fleet-backup.lock` for the generation publisher. The normal Backup-tab capture path and CLI `backup-fleet` path therefore do not rely on their front ends to remember the outer lock. A caller that already owns the outer lock must pass `operation_lock_held=True` to avoid a nested non-reentrant flock; pack apply and WorldTab multi-step operations use that explicit contract. Read-only listing/deep verification does not take the operation lock; restore/export paths that must protect retention or a live-world rename are wrapped by the owning worker.

- Pack update apply is correctly wrapped by both production callers: `PackUpdateDialog._start_apply()` holds the lock across the verified fleet checkpoint and `apply_update()`; CLI `cmd_update()` does the same and passes `operation_lock_held=True` to the nested backup.
- Pack rollback is **not** wrapped by either production caller. GUI `PackUpdateDialog._start_rollback()` directly calls `rollback_update()`; CLI `cmd_rollback()` does the same. `rollback_update()` itself does not acquire the lock. It renames the live server folder aside, restores a previous folder, and can move current world folders across. A scheduled/manual fleet backup or world mutation can therefore overlap that rename and observe a missing or intermediate server path.
- Previous-install pruning is also unguarded: GUI `_start_prune()` and CLI `cmd_prune_previous()` call `prune_previous_installs()` directly, and that helper does not acquire the lock. This can race a rollback trying to consume the same previous-install tree.
- World swap/reset/wipe/legacy restore workers correctly hold the fleet lock across checkpoint and mutation. Full-server restore also uses the lock. However, the visible Worlds tab button `Clean up old world copies` is wired directly to `_cleanup_pre_swap_dirs()`, which calls `BackupManager.prune_pre_swap_dirs()` synchronously without the lock, a fresh stopped-state check, or a fleet checkpoint. The separate `_WorldOperationWorker` has a `cleanup` branch that takes a checkpoint and checks stopped state, but no production call site invokes `_start_fleet_action("cleanup")`; the button bypasses that safer worker path.
- World ZIP label rename/delete use the fleet lock, and the full-server backup restore worker uses it as well.

Before Rust extraction, centralize lock acquisition at each mutation boundary or provide a clearly documented caller-owned-lock API and ensure *every* GUI/CLI caller follows it. Avoid nested non-reentrant `flock` acquisition: the apply-update path deliberately owns the outer lock while its backup callback calls `run_backup(operation_lock_held=True)`. Add inter-process contention tests for rollback, prune, and pre-swap cleanup, and assert the user-facing operation returns a busy result without changing paths. This lock must remain an OS-level cross-process primitive; an in-process Rust mutex would not protect against the scheduler or a second Crucible process.

**Pack-update runtime preflight does not yet use the full process-scan contract:** `_update_safety_blocker()` re-probes `probe_running()` and the configured IPv4 listener check immediately before backup/staging and again before the live rename. It does not inspect the instance's unmanaged Java PID association. Since `probe_running()` returns `False` when tmux is missing, a non-tmux JVM is only caught if its configured IPv4 port appears in `/proc/net/tcp`; a JVM can still be using files during early startup or shutdown without a listening socket. The shared tri-state process observation should be included here before rename, not just in `TmuxManager.start()` and removal. Rollback uses the same blocker and shares the same gap.


### 2.5.3 Mod inventory, download, and replacement boundaries

**JAR inventory and metadata are a reasonably clean pure-data seam:**
- `ModManager.list_mods()` enumerates top-level enabled `.jar` and disabled `.jar.disabled` files, plus nested JARs displayed as bundled/unmanageable. It does not parse every archive during the first list pass; the Qt tab starts a generation-tagged background inspection worker for rows without metadata.
- `inspect_jar()` reads a bounded metadata member (4 MiB maximum) from a JAR ZIP and recognizes Fabric `fabric.mod.json`, Quilt `quilt.mod.json`, Forge/NeoForge `mods.toml` / `neoforge.mods.toml`, legacy Forge `mcmod.info`, and `META-INF/MANIFEST.MF`. It reads only the first declared mod entry in several formats. Side semantics are deliberately conservative: explicit `client`, `server`, and `*` values map to Client/Server/Both; Forge TOML is marked Client only for `clientSideOnly=true`, otherwise Unknown; `displayTest` and dependency metadata are not treated as execution-side evidence; missing/unsupported/invalid metadata stays Unknown. Unknown must not become Both or compatible by default.
- `ModEntry` is a useful language-neutral record candidate (filename, enabled, size, name/id/version/description/url, explicit side, bundled). A Rust parser could accept bounded metadata bytes plus an explicit format identifier and return this record. Keep ZIP central-directory traversal and bounded extraction in Python initially; do not make Rust parse an entire JAR merely to read a 4 MiB metadata member.
- `inspect_jar()` currently calls `namelist()` before reading the one metadata member, so a hostile JAR with an extremely large central directory can still impose directory-memory/CPU cost even though the selected metadata body is capped. There is no dedicated JAR entry-count or central-directory size limit in this path. It runs in a worker, so it avoids blocking the Qt event loop but not total memory/CPU use. Measure with synthetic high-entry-count JAR fixtures before choosing an archive crate or adding a safe entry-count bound.

**The file-mutation routes do not share one transaction/lock contract:**
- Enable/disable in `ModManager.enable()/disable()` use `Path.rename()` to remove/add `.disabled`. There is no explicit destination-exists guard or shared mod-change lock. On Unix, Python documents that `Path.rename(target)` silently replaces an existing file target when permitted; therefore enabling `foo.jar.disabled` while `foo.jar` already exists can overwrite the currently enabled JAR, and disabling can overwrite an existing `foo.jar.disabled` copy. This is OS-sensitive (Windows raises on an existing target). Crucible is Linux-first, so this is a real data-preservation edge, not merely a cross-platform nuance. Reference: [Python 3.11 pathlib Path.rename](https://docs.python.org/3.11/library/pathlib.html#pathlib.Path.rename).
- Delete is a direct `unlink()`; Add from file is a direct `copy2()` after validating a JAR and refusing a different same-name file. These methods do not acquire `.crucible/mod-change.lock`, do not stage/verify an entire transaction, and do not independently require a stopped server. The Mods tab checks `TmuxManager.get_status() == "stopped"` in its GUI action path, but this guard lives outside the mutation helper. The file picker is opened after that check, and Delete presents a confirmation dialog after it; neither repeats the check immediately before the final mutation.
- Version replacement through `mods/versions.py::replace_files()` is better protected. It validates safe unique filenames and required SHA-1 values, obtains an exclusive per-instance `.crucible/mod-change.lock` via `O_CREAT|O_EXCL`, downloads/verifies all selected files in a temporary staging tree, re-hashes the original, invokes an optional `before_commit` callback, copies affected originals and the prior `added-mods.json` into `.crucible/mod-history/<id>/`, writes a receipt, publishes replacement files with `os.replace()`, updates the identity record, and rolls published files/metadata back on ordinary exceptions. If the process dies mid-change, the lock/history directory are deliberately left for manual recovery.
- AddModDialog and the Change Version path pass a last-moment `TmuxManager.get_status() == "stopped"` callback to `replace_files()` after dependency resolution/download. The callback is valuable but uses the same existing status/process-scan implementation; the previously identified incomplete-/proc/unmanaged-Java gap means it is not yet a complete process-absence proof.
- The version-replacement lock is **not** the fleet backup lock. `replace_files()` does not acquire `fleet_operation_lock()`, and FleetBackupManager does not inspect `mod-change.lock`. A backup can therefore run while a multi-file replacement deletes old JARs, publishes new JARs and changes `added-mods.json`. The fleet snapshot is a whole-server-tree snapshot and can capture an intermediate set. Conversely, the fleet operation lock does not stop a direct ModManager add/delete/enable/disable or a pack-index download. `FleetBackupManager._snapshot_instance()` captures the registered server tree; `_walk_server()` excludes selected transient folders/files but not `.crucible/`, `.crucible/mod-change.lock`, `.crucible/mod-history/`, receipts or `added-mods.json`. Therefore an interrupted `replace_files()` lock is treated as ordinary snapshot content and does not block a generation; a generation can preserve a mid-transaction file set plus the stale lock/receipt rather than requiring manual recovery first. The fleet snapshot does have per-file descriptor/stat checks and a second structural inventory walk, which catch many concurrent changes; the gap is absence of the mod transaction's lock state as a precondition, not absence of snapshot integrity checks. The existing `test_global_operation_lock_prevents_backup_during_world_or_pack_mutation` only manually acquires the global lock inside the test, so it does not prove production mod callers acquire it or that a stale mod-change lock blocks backup.
- Dependency verification in `ModsTab._verify_deps()` checks stopped status before starting its network worker, but after it resolves missing dependencies it calls `modrinth.install_files()` directly. That helper downloads/writes files one by one to live `mods/` and saves the record best-effort; it does not use `replace_files()`, the per-instance lock, a final stopped-state callback, or the fleet operation lock.
- The pack-index download UI calls `_require_stopped()` once before opening DownloadModsDialog. The worker then calls `download_pack_mods()` over one or more network downloads; the downloader has no process-state callback or transaction lock. It stages each individual file to a temp file and atomically renames it into `mods/`, but a long download batch can continue after the server starts and a concurrent fleet backup can see a partly-updated pack.
- Manual Add JAR checks stopped status before the file picker and then uses direct `ModManager.add_from_file()`; drag/drop checks immediately before the direct copy. The direct copy itself is not staged/locked and is not revalidated at publication time.
- `modrinth.install_files()` and `download_pack_mods()` are separate from `replace_files()`: they use per-file temporary download paths and atomic per-file rename, but they are not a multi-file transaction. When a SHA-1/SHA-512 is present they verify it; when no hash is supplied, the indexed downloader accepts a non-empty file. The pack index's declared size acts as an upper bound, not an exact-length assertion, when no hash exists. Modrinth direct-install also only compares SHA-1 when supplied. These are different integrity levels and should not be flattened into a single VerifiedDownload boolean.
- The two `ModsTab._set_enabled()` methods are both present in the class; the later definition shadows the earlier one at runtime. This is not an execution-speed issue, but it means the earlier selection-preserving implementation is dead code and can mislead readers of the first definition.

**Required safety work before Rust owns any mod-file effect:** centralize the stopped/process check and operation serialization at the file-mutation boundary. Mod changes that must be consistent with a fleet generation should coordinate with `fleet_operation_lock()` (with an explicit already-held API for nested work, as used by pack apply); do not assume `.crucible/mod-change.lock` protects a backup. Use no-replace publication for enable/disable and Add where overwriting is not intended; preserve previous bytes before intentional replacement. Recheck the server's process state immediately before commit, and do not map an incomplete process scan to stopped. Make the multi-file dependency/download batch either a proper stage/receipt transaction or explicitly expose partial progress and safe recovery.

**Rust extraction boundary:** first candidate is pure parsing/classification of supplied bounded metadata bytes into `ModEntry`/explicit side evidence, then possibly a pure dependency graph validator that receives the full compatible-release candidate set as input. Do not move JAR download, file copying, rename/delete, history/receipt writing, lock acquisition, server status checks, or UI/confirmation into the first Rust crate.

**Existing coverage gap:** there is no dedicated `test_mod_manager.py`, `test_mod_versions.py`, or `test_downloader.py` in the current test tree. `test_security_boundaries.py` has one oversized JAR-metadata case; `test_curseforge_downloads.py` covers provider disablement, safe URLs, selected update/replacement and pack-index blocked fallback; the generic security tests do not prove all Mods-tab mutation callers acquire one shared lock. `test_fleet_backup.py::test_global_operation_lock_prevents_backup_during_world_or_pack_mutation` only tests backup refusal while the test explicitly owns the outer lock; it does not call a production mod-change route. Add fixture coverage for metadata formats/side unknowns, huge ZIP central directories, duplicate enabled/disabled filename pairs on Unix, concurrent target appearance, server start during each download action, an interlock test that starts a backup during `replace_files()` and verifies it returns busy before copying, stale mod-change lock refusal/recovery, process-scan incomplete at commit, dependency install partial failure, no-hash/short-size archive entries, interrupted history recovery and rollback after each published file.

### 2.5.4 Crash-driven mod quarantine is another live mod writer

diagnostics/loadcheck.py separates read-only crash analysis from a mutating repair step:
- latest_crash_text() reads a bounded recent crash/log tail (16 MiB); _read_zip_text() bounds individual JAR metadata reads at 4 MiB. The parser recognizes invalid dedicated-server client classes, failed-mod blocks, named offender JARs, missing dependencies and duplicate-mod messages.
- jar_modids() reads Fabric JSON and Forge/NeoForge TOML metadata; jar_is_client_only() uses the explicit Fabric environment=client marker. These routines use ZIP namelist() before reading bounded members, so the central-directory memory/entry-count exposure is shared with ModManager.inspect_jar().
- diagnose_server(), parse_crash_log(), map_modids_to_jars() and scan_client_only() are read-only analysis candidates. autofix_loading(apply=False) returns a proposed quarantine list; apply=True calls quarantine_jars() and renames files.
- CLI crucible fix-loading <name> --apply calls autofix_loading(..., apply=True) directly. CLI --restore directly calls restore_quarantined(). The handler does not call TmuxManager.get_status(), does not require a confirmed stopped server, and neither helper acquires .crucible/mod-change.lock or the global fleet operation lock. This makes crash repair another independent writer that can run during a live server, a backup, a version replacement, or indexed download.
- quarantine_jars() renames each supplied JAR to <filename>.jar.disabled one by one. It has no no-replace destination guard; on Unix, rename can replace an existing disabled destination. Per-file errors are swallowed and the loop continues, so the operation may partially apply. Only after the file loop does it update .crucible/quarantine.json.
- _record_quarantine() appends records to that JSON file but does not atomically stage/replace it or reject a symlinked log path. It catches parse/read failures by discarding the prior in-memory records and catches write OSError silently. The record is therefore advisory and may not prove which files were actually quarantined.
- Critical restore semantics mismatch: restore_quarantined() does not read .crucible/quarantine.json. It enumerates every mods/*.jar.disabled file and renames any whose original .jar destination is absent. Therefore --restore can re-enable files that the owner had manually disabled and that Crucible never quarantined. The help text/comment says “re-enable mods Crucible previously quarantined”, but the implementation restores all disabled top-level JARs. It does leave a conflicting currently-enabled destination untouched, but there is no ownership marker for the disabled file.
- Unlike a multi-file replacement, there is no quarantine transaction receipt with preimage hashes, no recovery status, no lock, and no rollback if the process is interrupted partway through. A crash between renames and _record_quarantine() leaves disabled files with no corresponding log record; since restore ignores the log today this does not prevent re-enabling them, but it makes provenance unknowable.

**Boundary recommendation:** keep crash parsing/JAR metadata mapping pure and return a proposed exact path set plus evidence. Before any effect, require a fresh complete stopped/process observation and the same process-wide operation serialization as other server-file mutations. Quarantine should use a no-replace rename, preserve original hashes/paths and a transaction receipt before publication, and report partial/recovery state explicitly. Restore only entries recorded by a validated quarantine receipt and whose current disabled-file hash still matches the recorded post-quarantine bytes; do not sweep all *.jar.disabled files. Keep the owner-visible preview/confirmation in the CLI or GUI Python layer.

**Coverage gap:** the current test tree has no dedicated test_loadcheck.py. Add fixtures for crash-log parsing, exact JAR-to-mod mapping, large central directories, conflicting active+disabled basename, disabled files that were manually disabled, log corruption/symlink/write failure, partial quarantine/interrupted receipt, server-start-during-apply, fleet-backup contention, stale process scan, and restore limited to the receipt's entries.

### 2.5.5 Registered-server CLI and Setup actions bypass common effect guards

The GUI has different safety coverage depending on which tab exposes the same underlying domain operation. The following current production paths modify a registered server root but do not require a common process/operation-transaction boundary:

- Pack-index download: CLI cmd_download_mods() resolves the instance and calls download_pack_mods() without asking TmuxManager for status. ModsTab._download_from_pack() checks _require_stopped() once before opening the modal dialog, but SetupTab._download_mods() has no stopped check at all. The download worker then publishes files individually and has no action-time server-state callback, per-instance mod lock or fleet-operation lock. A server started from another process during the transfer is not detected.
- Mod dependency installation: ModsTab._verify_deps() checks stopped state before starting the worker, but its background function eventually calls modrinth.install_files() directly. It does not re-check state before each publication or coordinate with mod-change/fleet locks.
- Dedicated server loader install/repair: CLI cmd_install_server() calls serverloader.install_server_loader() on the registered folder without a stopped check or fleet lock. SetupTab._install_server() likewise shows confirmation and dispatches _ServerInstallWorker without calling TmuxManager.get_status(). The installer downloads a launcher/installer and writes or executes it in the existing server root (Forge/NeoForge/Quilt run vendor Java installers in that working directory). SetupTab.has_active_operation() prevents this same GUI's Start button while its own install thread runs, but it does not protect CLI/another Crucible process or the fleet backup scheduler. The helper itself only expands the target path and calls mkdir(exist_ok=True); it does not reject a symlinked root, hold a no-follow directory descriptor, or verify that the root is the same object before each publication. InstanceManager resolves the registered path on load, but that does not prevent the directory from being replaced by a symlink afterward. _download_to() creates temporary files under target subdirectories and calls os.replace(); the installer subprocess runs with cwd=target. create_fresh_server() checks target.is_symlink() before calling the same helper, but that outer check is not repeated in install_server_loader() and is subject to a path-replacement race. Forge/NeoForge/Quilt _run_installer() calls do not receive the cancel event, so cancelling the UI after the vendor Java subprocess starts does not interrupt that installer before its 900-second timeout. Successful installer JAR cleanup is not in a finally; failures can leave the downloaded installer and partial launcher libraries/scripts in the target.
- Server properties repair: CLI cmd_fix_properties --apply calls properties.autorepair_file() directly without a stopped-state check or fleet lock. SetupTab._fix_properties() opens PropertiesFixDialog without a stopped check; PropertiesFixDialog._apply() loads, rewrites and saves server.properties directly. It copies server.properties.bak only if one does not already exist, swallows backup-copy errors, and calls PropertiesDoc.save() to replace the file. The GUI start path runs a separate best-effort auto-repair only after its world/start gate, but that does not protect the explicit Setup/CLI repair actions.
- EULA write: CLI cmd_accept_eula() and SetupTab._accept_eula() call ServerInstance.set_eula_accepted(True) without a stopped-state check or operation lock. This is lower impact than JAR/launcher/config mutation, but it is still a file writer in the same server root and must have a defined policy if server-root effects become a shared Rust boundary. ServerInstance writes by temporary-file replace, but neither entry point first verifies a real non-symlink server root or revalidates the server state at publication.
- Seed/config edit: WorldTab._set_seed() does check TmuxManager.get_status() == stopped and calls the panel configuration guard before prompting; its atomic rewrite of server.properties does not take fleet_operation_lock(). This is better gated than the Setup property dialog, but a fleet snapshot can still overlap the write. Its temp-and-replace makes a single-file old-or-new result likely, but it does not establish transaction serialization.

Do not treat a modal confirmation or an initial stopped check as a mutation boundary. Dialogs, network waits and installer subprocesses can take time; a second process can start the server or take a fleet backup during that interval. The central repair is one shared effect-adapter policy: fresh complete process observation immediately before publication, a per-server mod/config/launcher operation lease where appropriate, and the fleet OS lock whenever the operation changes bytes a fleet generation claims to capture. Worker results should distinguish safe per-file publication from a multi-file partially-applied batch.

The same operation policy should be shared by CLI and GUI; it should not be recreated as one check in each front end. The first Rust helper should not call these writers. It may return validation/decision data, but Python should retain the lock owner, process probe, confirmation and filesystem publication until every call site has been migrated to one tested adapter.

### 2.5.6 GTNH pack update, rollback, and pruning are distinct transactions

**Update planning and apply**
- The review layer (`pack_update_model.build_preview()`) identifies pack identity, resolves either the release index, a custom URL or a local archive, probes archive central-directory metadata, and asks the planner for preservation/carry-forward and blockers. The planner docstring says “Never touches the filesystem”, but `plan_update()` reads the server root, server.properties, world directories, recursive directory sizes and free disk space. It is a read-only filesystem adapter, not a pure planner input.
- The planner's `running` argument defaults to `False`; production GUI obtains `model.resolve_running()` if it cannot reuse a status, while CLI supplies `TmuxManager.probe_running()`. The value is tri-state and unknown blocks. The plan is still a snapshot: preserve paths, mod carry-forward set and free-space estimate can become stale during owner confirmation.
- GUI apply and CLI update correctly hold `fleet_operation_lock(fleet.root)` across the mandatory complete fleet backup and the full `apply_update()` workflow. The backup callback deliberately uses `run_backup(operation_lock_held=True)` to avoid reacquiring the non-reentrant outer lock. This outer lock protects backup/pack update from one another; it does **not** prevent a separately running server from starting after the final status/port check unless Start also participates in a common process-operation lease.
- `apply_update()` rechecks the server/port before backup and again just before live rename, requires a verified fleet-generation callback before download/staging, validates the archive as a server pack, extracts beside the live root, overlays the reviewed preserve list, carries selected owner-added mods, then renames live to a timestamped previous tree and staging to live. A failure after the first rename attempts to put the previous tree back; after a successful swap the previous complete tree is kept unless `keep_previous=False`.
- The final status/port recheck is a check-then-rename sequence. There is no shared lock/lease shown in the server start path around the same probe and the live-root rename, so a concurrent independent Start can race in the gap after the check. The port probe also remains an IPv4 configured-port check, not a complete association scan of every Java process. Preserve the current checks, but do not call them an atomic no-JVM guarantee.
- Archive download uses a predictable sibling `.part` path opened with `Path.open("wb")` before replacing the final archive. Unlike Modrinth's tempfile/mkstemp downloader, it does not create the temporary name exclusively or use no-follow open; a pre-existing `.part` symlink can redirect/truncate its target. It enforces HTTPS, a 20 GiB byte limit and declared-length match when Content-Length is supplied, but it does not hash the pack download. The archive is subsequently structurally probed and extracted with path/symlink/size/ratio checks; structural validation is not publisher authenticity.
- `_write_receipt()` records the source version/variant/archive and pack-vs-carried mod baseline for future exact diffing. It publishes with temp+replace but catches OSError silently; the pack update can still report `ok=True` without a durable provenance receipt. Missing receipt changes future identity/carry-mod decisions. Receipt creation should become a required post-swap stage with explicit recovery if it is essential to future correctness.
- Preserve-copy validates nested symlinks/special files before and after copying; files use `copy2`, directories are copied as trees into fresh staging. The carry-mod loop copies selected live JARs directly without a per-file before/after digest comparison at that point; the fleet backup and earlier plan do not automatically make the current live file immutable during the whole operation. A concurrent external mod edit can result in a carried JAR different from the one reviewed.
- The update's `UpdateResult.ok` is false on ordinary stage/apply failure and the live server remains unchanged before the swap; if a post-swap receipt or late result failure occurs, rollback is attempted. The previous tree and fleet checkpoint are separate recovery assets and must remain distinct.

**Rollback**
- `rollback_update()` checks the caller's preliminary running value and freshly probes configured tmux state/port immediately before moving the live root aside. It keeps the current install as a sibling tree and renames the chosen previous tree into place, so normal rollback does not delete the replaced install.
- Production GUI and CLI rollback callers do not hold `fleet_operation_lock()` and the helper does not acquire it. A scheduled backup, pack update or world transaction can overlap the pair of root renames; the rollback path can transiently leave the registered path absent or partially switched.
- Previous-install discovery accepts any sibling matching the name glob for `<server>.pre-update-*` where `Path.is_dir()` succeeds. For an explicitly selected tree, rollback checks parent/name marker and presence of `mods/`, but does not reject `prev.is_symlink()` or pin the directory inode/content identity. A same-parent symlink named like a previous install and pointing at an external tree with `mods/` can pass these checks and be renamed into the registered live path. There is no manifest/hash receipt proving the previous tree is the actual one created by Crucible.
- If `keep_current_world=True`, rollback removes any same-named world directory in the restored tree with `shutil.rmtree` and then moves the current world over it. This is an explicit world-selection policy, not a byte-preserving rollback of both worlds. The old pre-update generation is expected to remain available in the fleet checkpoint, but the result does not separately list which prior-world directory was replaced.
- If a failure occurs after moving the live root aside but after the prior tree has become the live root, the current exception recovery only renames `aside` back when `live` is absent. That is not a complete journal for a partially completed `keep_current_world` overlay; a failed world move can leave a partially carried world while the function reports rollback failure. Add injected-failure coverage and a recovery receipt for each destructive substep.

**Prune**
- `prune_previous_installs()` selects all but the newest `keep` sibling trees and recursively deletes them. Neither GUI nor CLI production caller takes the global operation lock; the helper does not acquire it, recheck a running server, or take a fresh backup. It can race rollback consuming the same directory.
- Previous-install discovery follows `is_dir()` on a matching name and does not reject symlinks before creating the candidate entry. `shutil.rmtree` will refuse to recursively remove a symlink on supported Python, but the candidate should still be rejected as untrusted before any size/traversal logic or rollback use.
- The GUI's preview is built before the owner confirmation; it does not pin the exact set of path/inode identities selected for pruning. The destructive helper re-enumerates the tree after confirmation, so a new matching sibling created between preview and execution can be removed without appearing in the confirmed list.

**Existing tests and gaps**
- `tests/test_pack_update.py` exercises identity/version planning, tri-state status blockers, preservation, stage/swap, archive safety, fleet-backup callback requirement, cancellation-before-work and repeated status/port checks; it also tests that rollback re-probes after the dialog preview.
- `tests/test_pack_update_sources.py` covers release/source parsing, foreign-directory rejection, no-mods trees, keeping the replaced install and current-world carry behavior, and simple prune retention.
- The current test set does not cover previous-tree symlink injection, content/receipt authenticity of a previous tree, cross-process fleet-lock contention for rollback/prune, a new matching tree appearing after the prune preview, process start between final probe and rename, predictable `.part` symlink redirection, missing receipt write after successful swap, or injected failures during a `keep_current_world` overlay. Add these before any Rust implementation or optimization of pack update/rollback/prune.

**Rust boundary:** a pure GTNH identity parser, version comparator, preserve-plan classifier and deterministic carry-mod decision can later be extracted when all observed files/hashes/loader metadata are supplied as immutable input. Keep downloads, ZIP probing/extraction, backup locks, tmux/port/process probes, filesystem staging, rename transactions, rollback/pruning and receipt publication in Python until those effects have one shared, tested transaction owner.


### 2.5.7 Player lists, recently-played state, avatar fetches, and config editing

**Player-list data and effects**
- `PlayersTab` displays join/leave events from `LogWatcher`; the parser recognizes names with `\w+`. The recently-played map is stored under each server's `.crucible/players_seen.json`, with first/last-seen timestamps, session count, and locally tracked playtime.
- `_read_json_file()` caps these JSON reads at 16 MiB, but follows symlinks and does not validate a common schema. `players_seen.json` accepts any object whose values are dictionaries. `whitelist.json`, `ops.json`, and `banned-players.json` are assigned directly to `_data` without verifying the root is a list or that each row has safe string `name` and `uuid` fields. A syntactically valid wrong-shaped JSON document can therefore break table rendering or flow into later path/command handling.
- Adding whitelist/operator entries uses a live console command after a single `probe_running()` check, then reloads the file after 1.5 seconds. Removing an entry is different: `_remove_player()` deletes from the in-memory list and `_save()` directly rewrites the JSON file. This path is used for whitelist, ops, and banned lists and does not update the running server's in-memory player-list object, check whether the server is running, acquire the fleet operation lock, preserve a preimage, or recheck the file before publication. While a server is running, disk and in-memory permissions can diverge until reload/restart and the server may later persist its own view. Prefer the matching console operations (`whitelist remove`, `deop`, `pardon`) for a confirmed managed session, and a stopped/locked file transaction otherwise.
- The JSON writer uses a fixed sibling `.tmp` path with ordinary `write_text()` and `replace()`: no exclusive/no-follow temp, file fsync, directory fsync, operation lock, or surfaced rollback. The UI mutates `_data` before writing; an `OSError` is not caught inside `_save()`, so the visible table can show a removal that was not saved. The write path is also synchronous from the Qt button handler, and a fixed `.tmp` file can be collided with or followed if it is a symlink. The player-list screen's UI state is not reloaded from disk after a failed commit.
- `_save_seen()` writes `.crucible/players_seen.json` by the same fixed-temp pattern and silently ignores `OSError`. It is called during join/leave and on server-stopped/log-rotation handling. Its write failure is not surfaced, and the file is read/written without a per-server state/lock contract. More specifically, `_record_seen()` is called directly from the `player_joined`/`player_left` Qt slots and `_save_seen()` serializes the entire `_seen` dictionary and writes/replaces the full file on that same event/UI thread for every event. The reader's 16 MiB cap does not bound the number of in-memory records; no expiry/retention policy prunes names. A long-lived server history therefore makes each subsequent event increasingly expensive and can stall player-list UI updates. This is a source-confirmed cost, but no event-handler latency has been measured. A Python-side debounce/coalesced writer is the first candidate; preserve dirty state and flush on stop/close, and only clear dirty after a successful atomic publication.
- `_uuid_for()` trusts the `uuid` field from `usercache.json`, `whitelist.json`, or `ops.json` and passes it directly into `<world>/stats/<uuid>.json`. There is no UUID syntax check or resolved-path containment check. Malformed local JSON can make the UI probe a path outside the world stats directory. Validate a canonical UUID/legacy accepted form before constructing this path and verify containment/no-follow before opening. The stats file itself is opened through `_read_json_file()` with the 16 MiB read bound, but the candidate `world/stats/<uuid>.json` path is checked with `Path.exists()` first and then opened later; a symlinked stats file is followed. Preserve no-follow/root-containment checks at the final open boundary, not just a string-format check.
- Existing Qt coverage is `test_player_avatar_states_qt.py`: success/error/stale-cache/loading states, thread retention during close, stale generation rejection and static placeholders. It does not cover player-list JSON shape, add/remove semantics, running-server file edits, fixed-temp symlink/collision, write failure, recently-played persistence, or UUID path containment.

**Avatar fetch and cache**
- A join event starts one short-lived `QThread` per distinct player name. Requests use `https://minotar.net/avatar/<name>/20`, default `urllib.request.urlopen()` redirects, an 8-second timeout, and a 2 MiB encoded-body cap. The cache TTL is seven days; valid stale data is used after network failure. The code does not enforce HTTPS/host policy on every redirect hop, inspect content-type, or impose a decoded image width/height/pixel ceiling before `QImage.fromData()`. The 2 MiB cap applies only to network bytes: `_valid_png()` calls `QImage.fromData()` immediately and has no dimension/pixel ceiling. The stale-cache path calls `cache.read_bytes()` without checking cache file size first, and `_avatar_for()` separately loads a cache entry with `QPixmap(path)` without passing through `_valid_png()`. Thus compressed response size does not bound decoded memory, and an oversized local cache file is unbounded on those paths. This is an unmeasured resource-risk hypothesis; Qt's decoder already does the actual image decode in native code, so Rust is not the obvious fix. Inspect dimensions before full decode, bound cache reads, and reject excessive pixel counts in Python.
- Each fetch writes `<name>.png.partial` with ordinary `write_bytes()` and then replaces the cache file. The temporary name is deterministic and not opened exclusively/no-follow. Multiple app instances or colliding workers for the same name can contend for it; a pre-existing partial symlink can redirect the write. Player names from the join regex cannot contain slash/path separators, but the cache still needs a safe leaf-name contract and no-follow temporary publication.
- Requests are not managed by a bounded queue. The tab suppresses duplicate pending names within that one instance, but a burst of unique joins can create a burst of threads and simultaneous network requests. Unlike Add Mod's bounded prioritized 48-item icon queue, this avatar path has no in-flight cap or pending limit. Benchmark a synthetic join burst and bound the worker queue/concurrency if it has visible CPU, thread or network impact; keep cache fallback and stale-generation behavior.
- Do not port avatar download, image decoding, or Qt thread lifetime to the first Rust core. If the HTTP path is later consolidated, apply the same per-hop HTTPS, timeout/body, redirect-count and provider policy as other untrusted remote content.

**Current test evidence and missing coverage**
- `tests/test_player_avatar_states_qt.py` covers avatar success/failure, stale-cache fallback, worker/thread retention on close, stale-generation suppression and visual states. It does not cover encoded-size-vs-pixel limits, hostile redirects, unbounded stale-cache reads, deterministic `.partial` collisions/symlinks, or join-burst concurrency.
- The current test tree has no dedicated player-list/history persistence test module and no dedicated ConfigTab/NotesTab save-contract suite. `test_core.py` covers the tmux literal-input boundary, but does not validate player command argument policy or JSON permissions-list shape and mutation semantics.
- No test currently demonstrates that a player join/leave handler remains responsive with a large `players_seen.json`, that a failed history write remains dirty/retryable, that history retention is bounded, or that a malformed UUID cannot escape the selected world's `stats/` directory.

**Coverage and persistence contention notes**
- There is no `test_notes_tab.py`, `test_config_tab.py`, or `test_system_tab.py` in the current test tree. `test_resource_monitor.py` has only three matching cases (exact marker/Java fallback and avoiding false matches); all stub `_iter_pids()`, so the real `os.listdir('/proc')` failure path is not covered. `test_machine_resources.py` verifies its aggregate process matcher and GPU unavailable states, but not the visible SystemTab timer or GUI responsiveness.
- NotesTab's 500 ms timer writes through InstanceManager.update_instance(). That serializes the complete registry list on every save; it is not a field-level note write. A successful registry publication fsyncs the temp file, then replaces the file. There is no directory fsync, exclusive/no-follow temp creation or inter-process flock. Two GUI/CLI InstanceManager objects can both pass the stat-signature check and race over the fixed instances.tmp path using stale snapshots, causing lost updates. The current tests exercise one manager's external-edit detection and disk-first in-memory commit, not two simultaneous writers.
- A NotesTab save failure displays an error but unconditionally clears `_dirty`; `load()` then switches the displayed notes and may discard the uncommitted buffer. A failure retry/retention test is absent. Keep this persistence behavior in Python until it has a committed/not-committed result and cross-process transaction contract.

**Config and notes tabs**
- `ConfigTab` is a fourth, independent server.properties reader/writer in addition to `PropertiesDoc`, `ServerInstance.world_level_name()/server_port()`, and pack-update's parser. It strips each physical line, recognizes only `=`, stores last duplicate value in an `OrderedDict`, and preserves the final value text from the stripped line. During save it iterates original lines and writes the selected final value to every duplicate occurrence, normalizes each matching line to `key=value`, and emits LF with a final newline. It does not preserve duplicate-value distinctions or original separators/spacing.
- ConfigTab's Save slot writes a fixed `.tmp` sibling with `write_text()` then replaces `server.properties`. It does not back up the original, fsync the temp/directory, use no-follow/exclusive creation, take `fleet_operation_lock()`, or revalidate that the server is stopped immediately before publication. It can therefore race a live server's in-memory config and a fleet snapshot. Its dangerous-key confirmation is a user warning, not a stopped/process lease.
- `NotesTab` stores notes inside the registry record and autosaves after a 500 ms debounce by mutating `ServerInstance.notes` then calling `InstanceManager.update_instance()`. If the registry write fails, it shows an error but still sets `_dirty = False`; switching servers or closing then does not retry the save. This can lose the latest edit after an external-registry conflict or disk error. Keep debounce in the Qt layer, but change the persistence result so dirty state is cleared only after successful commit.
- Neither ConfigTab nor NotesTab has its own Rust-shaped algorithm worth porting. The reusable core candidate is only a pure parser/normalizer over supplied property text; all path reads, read-completeness, confirmation, locking, publication, registry writes and UI retry state remain in Python.

### 2.7 Qt application and worker surface

The GUI is divided into:

- Top-level workspace: `main_window.py`, `instance_panel.py`, `sidebar.py`, `system_tray.py`.
- Task dialogs: add/import, add-mod, create-server, modpack, download, client export, pack update, player sharing, properties and shortcuts.
- Tabs: Console, Config, Mods, Notes, Info, Backup, Worlds, Players, Setup, System.
- Supporting modules: theme, icons, server tinting, thread lifecycle helper, pack-update presentation model.

Worker classes are generally small Qt adapters that call the existing synchronous domain function and emit a result/error signal. Examples observed include:

- MainWindow's persistent health worker calls `TmuxManager.status_map()`.
- InstancePanel owns persistent log-watcher and watchdog threads, and uses a worker for tmux actions/world-start inspection.
- BackupTab worker runs fleet backup, verification, restore, or scheduler tasks off the GUI thread.
- WorldTab workers perform world-size scans and checkpointed swap/reset/wipe/cleanup.
- Add/import, mod search/icon/resolve/install, modpack install, server creation/installation, client export, downloads, pack update, player avatar, and share upload each use bounded Qt worker patterns.

The shared `connect_thread_cleanup()` waits until the native QThread has actually stopped before releasing feature state. This exists because dropping a Python QThread wrapper after a timed wait caused a real process-abort class of bug. Any future FFI callback or Rust worker must preserve QObject/thread lifetime guarantees, not merely return the right value. Not every operation uses a permanent worker: `_run_tmux()` creates a short-lived QThread per command; the main health, log-watcher and watchdog workers persist; world-start inspections use tracked short-lived QThreads; Copy IP uses a daemon Python thread. These lifetimes and frequencies should be preserved/benchmarked individually rather than replaced by one generic Rust worker.

**Important distinction:** tabs defer some expensive *data loading* until first view, but `ui/tabs/__init__.py` imports all ten tab modules at module import time, and `instance_panel.py` imports the tab package. The InstancePanel then constructs eight tab widget instances immediately in `_build_ui()` and adds them to the QTabWidget; it does not lazily instantiate a widget when the tab is first selected. Thus neither tab-module imports nor widget construction are lazy. A meaningful startup optimization would have to defer both class imports and widget construction while retaining the current page-navigation, object-lifetime, and worker semantics. Measure before taking on that UI refactor.



## 2.8 Import-order and dependency-cycle observations

A line-level import audit distinguishes the following:

- `download_http.py` imports the provider adapters only inside request construction paths. `curseforge.py` imports the Modrinth adapter at module load, but imports shared `download_http` request helpers only inside its request function. Modrinth also imports download helpers, CurseForge, and `versions.py` inside the functions that need them; `versions.py` imports Modrinth at module load and imports CurseForge only inside provider-specific version functions. This is a deliberately deferred dependency knot, not evidence of a top-level `download_http ↔ curseforge ↔ modrinth ↔ versions` import-time cycle.
- `serverloader.py` imports Prism only inside the fresh-server workflow; `prism.py` imports pack-update detection inside a detection helper and imports serverloader only when optional server installation is requested. `pack_update.py` imports Prism's archive extraction helper locally inside the apply-update path (with an explicit comment that this avoids a cycle).
- Package facades intentionally use lazy attributes for selected exports: `crucible.data.BackupManager`, `crucible.process.LogWatcher`, and `crucible.process.Watchdog`.

These local imports reduce module initialization coupling but make first-use latency and import order path-dependent. A Rust migration should not flatten these dependencies into a single giant crate or move provider-specific logic into core types. Capture import-time and first-use profiles for the actual command path before trying to normalize them. Preserve lazy boundaries where they prevent optional Qt/network/provider modules from loading for unrelated CLI operations.



### 2.8.1 External network/provider adapters and a redirect caveat

The external I/O surface is intentionally split across multiple modules rather than one common client:

- `download_http.py` is the security-aware shared request/redirect layer used by indexed mod downloads and Modrinth JAR installs. It rejects non-HTTPS input URLs, credentials embedded in URL userinfo, unsafe ports and API-key query parameters. CurseForge authentication is attached only for its exact host set and is currently disabled before the key file is read. Authenticated/CurseForge redirects cannot leave the approved CurseForge hosts; generic requests are rebuilt without credentials.
- `downloader.py` uses that shared layer for modpack-index downloads. It has 64 KiB chunks, cancellation checks, 2 GiB per-file limits, 3 retry attempts, SHA-512 or SHA-1 verification where supplied, and same-directory temporary-file publication. A file with no provider hash is accepted only if non-empty, so do not silently change hash-absence semantics during a port.
- `modrinth.py` has API JSON requests capped at 16 MiB and a 12-second timeout. Its real mod download path uses the shared request opener and a 2 GiB limit. It still contains a separate `fetch_bytes()` utility that calls default `urlopen`; the current Add Mod dialog's icon worker instead calls the stricter `icon_fetch.py` path.
- `icon_fetch.py` is intentionally separate: only `cdn.modrinth.com` is enabled, redirects stay within the provider host allowlist, no credentials are sent, 8 MiB body cap, 8-second socket/deadline cap. CurseForge icon previews are blocked in code, not merely hidden in the dialog. `_IconWorker` uses a bounded 48-job queue, prioritizes selected/visible icons, suppresses obsolete results, and drains one network job at a time.
- `serverloader.py` has fixed public Mojang/Fabric/Forge/NeoForge/Quilt endpoints, 30-second timeout, three retries, 16 MiB metadata cap, 2 GiB download cap, 64 KiB streaming and `.part` same-directory temporary files. It uses Python's default `urlopen` redirect handler.
- `pack_update.py` obtains GTNH server URLs from the authoritative `versions.json` index or accepts an explicit owner-supplied HTTPS source. It caps metadata at 16 MiB, server packs at 8 GiB, streams 256 KiB chunks, supports cancellation and staging, and uses default `urlopen` for the initial fetch/download. It does not construct GTNH archive URLs from version names.
- `gofile.py` is not an urllib client: it opens a direct TLS connection to fixed `upload.gofile.io/uploadfile`, guest-first, optional owner token only in Authorization, hashes and rechecks the same no-follow file descriptor, streams 256 KiB chunks, checks upload hash and file identity again, and honors cancellation before the final multipart boundary. Response size is capped at 1 MiB; the returned link must be an HTTPS `gofile.io`/`www.gofile.io` download page of the expected `/d/<id>` shape. Optional remote size/MD5 are not claimed verified when omitted.

A source/redirect audit also found a pre-existing HTTPS-policy gap: `serverloader.py` and `pack_update.py` validate the *initial* URL as HTTPS but use the default `urllib.request.urlopen()` opener. `modrinth._get()` and its older `fetch_bytes()` helper also use default `urlopen()` with no custom redirect validation. The Python 3.11 and 3.13 standard-library docs explicitly describe the default `HTTPRedirectHandler` as accepting redirect targets on HTTP, HTTPS or FTP schemes. Therefore an original HTTPS URL is not by itself an end-to-end HTTPS guarantee for these paths. This matters for server installers and modpack archives that contain executable code. The shared downloader and icon fetcher have custom redirect controls; other paths need an explicit HTTPS-on-every-hop policy and regression tests before Rust replaces them. Preserve legitimate cross-host HTTPS CDN redirects where the source design requires them; a strict provider host allowlist is appropriate for icons/authenticated endpoints but not necessarily for arbitrary user-supplied pack archives. Do not add credentials to unauthenticated redirecting requests.

Tests already cover disabled CurseForge before key read/network, forged or non-HTTPS redirect targets in the shared downloader, icon redirect allowlists and credential dropping, icon queue capacity/priority/cancellation/slow-drip deadline, and Gofile source mutation/hash/size/MD5/URL/cancellation/error redaction. Missing coverage should include explicit HTTPS-to-HTTP and HTTPS-to-FTP redirects in every default-urllib path, while preserving normal cross-host HTTPS CDN behavior.

## 3. Important end-to-end flows

### 3.1 GUI startup and health status

1. `crucible gui` dispatch imports MainWindow and Qt.
2. MainWindow constructs InstanceManager, TmuxManager, persistent health thread, sidebar and InstancePanel.
3. The sidebar starts as Checking; the first health request is sent immediately.
4. A 5-second QTimer schedules status refreshes; `_health_busy` prevents overlapping requests.
5. `TmuxManager.status_map()` obtains the tmux session list once for the full instance list.
6. A registered session yields Running. For instances without a session, the code checks for an unmanaged matching Java process, then missing folder, then Stopped. Unknown query errors remain Unknown.
7. MainWindow applies one status map to the sidebar, selected panel and tray. The tray does not own another polling loop.

Performance implication: the session list is already batched. The remaining repeated discovery is per-instance unmanaged-process detection after a session miss. `machine_resources.py` contains a separate one-pass aggregate JVM scan; a shared per-instance PID map is a promising Python refactor to benchmark.

### 3.2 Server lifecycle

Start/stop paths use the shared TmuxManager, exact instance/session targets, state confirmation and action-time revalidation. Start includes world-selection inspection and may require an owner confirmation. LogWatcher recognizes the actual Minecraft ready/stopping lines. Watchdog coordination is driven through queued Qt signals. Heartbeat ordering prevents intentional Stop from being interpreted as a crash.

Do not split this state machine between Python and Rust. If a Rust core is used, it should initially return a pure eligibility/classification result from a caller-supplied snapshot; Python remains the only layer issuing tmux commands and presenting user confirmation.

The per-action tmux polling is another explicit performance boundary. After `tmux new-session`, `TmuxManager.start()` calls `_verify_started()` with a six-second deadline and 250 ms interval. Each iteration checks the exit-marker file and then calls `probe_running()` unless the marker appeared. A healthy start therefore runs roughly 24 `tmux has-session` subprocesses over the six-second grace window before the method returns. Early exit is caught by the marker/session checks; any optimization must retain immediate-failure diagnostics and not report success if the session died.

Graceful `TmuxManager.stop()` defaults to a 90-second timeout and 2-second polling interval. Each iteration calls `probe_running()`; while the tmux session persists, it calls `is_java_foreground()` and can send Ctrl-C to interrupt the GTNH wrapper's automatic-restart countdown. This can reach about 45 session probes plus up to 45 pane probes on the maximum-duration path. It is intentionally action-driven, not an idle poller, and its wrapper countdown behavior must not be removed. Benchmark only with isolated fake tmux responses or a disposable synthetic server, never by stopping the owner's live world.



### 3.2.1 Heartbeat and watchdog state are separate from live tmux status

The lifecycle model uses two related but distinct sources of truth:

- Live status comes from a fresh tmux/process observation. The GUI's cached five-second status map is presentation state only; destructive operations and lifecycle actions probe again.
- Crash recovery is an on-disk per-instance heartbeat under Crucible's state directory. It stores `state`, Linux `boot_id`, `tmux_session`, and `updated_at` when running is recorded. Stop-intent/clean-stop/handled-crash transitions preserve the prior boot/session metadata where present.

The observed heartbeat states are `running`, `stop_requested`, `stopped_clean`, and `crashed_handled`. Ordering is material: graceful Stop records `stop_requested` before the server is stopped (disarming watchdog restart); only confirmed completion records `stopped_clean`. If the machine reboots during a requested Stop, the old boot ID plus `stop_requested` still produces an owner-visible crash report. An uncertain tmux probe or missing boot ID is not treated as evidence of clean shutdown. A crash report is marked handled so it is not repeatedly shown on later launches.

`HeartbeatStore._write()` writes a same-directory temporary file, flushes/fsyncs the file, and publishes it with `os.replace()`. The code does not currently fsync the parent state directory after the rename. This makes the rename atomic to concurrent readers but is not the same as the full directory-entry durability protocol used by fleet backup publication. Record this as a durability question to assess separately; a Rust implementation must not claim stronger crash durability than it actually provides.

The watchdog is a Qt QObject living in its own QThread. It creates its QTimer only after `start()` runs on that thread. It polls every 10 seconds, requires two consecutive misses to confirm a crash, waits 30 seconds before an automatic restart, stops after three consecutive crashes, and resets the count only after 10 minutes of stable uptime. It separately tracks tmux-session misses and Java-foreground misses because GTNH-style wrapper shells can survive JVM exits. `stop_requested` disables restart while still observing a pending wrapper countdown. Restart re-runs world-start inspection and fails closed if the selected world is unsafe, unavailable, or requires an owner confirmation.

The current polling implementation does not match the watchdog module docstring's claim that one `tmux list-sessions` call covers every watched instance. `_poll()` loops over instances serially; for each watched server it calls `probe_running()` (`tmux has-session`, timeout 2 seconds), then, if the session exists, `is_java_foreground()` (`tmux list-panes`, timeout 2 seconds). This is up to two tmux subprocesses per watched server per 10-second tick, apart from heartbeat reads. The main window's five-second health worker separately does batch `list-sessions`, so this is a second observation path with a different process cost. With N healthy watched servers the watchdog can issue up to 2N tmux calls each poll; if commands time out, the serial loop can be delayed by seconds per instance. This is a source-confirmed count, not a measured latency benchmark. Benchmark at 1/5/20/50 watched servers and test a possible batch snapshot (`list-sessions` once plus a batch `list-panes` result) while preserving per-instance unknown/Java-miss/Stop-intent semantics. Do not replace per-instance uncertainty with one global false result.

Tests already cover heartbeat read/write transitions, reboot detection, same-boot interrupted Stop, cross-boot interrupted Stop, uncertain tmux/Java probes, wrapper-alive/Java-gone pending state, repeated crash confirmation, and Stop coordination. Preserve these as Rust/Python cross-implementation fixtures if watchdog logic is ever extracted. Do not move the QTimer, watchdog thread, restart scheduling, or tmux commands into Rust as a first slice.

### 3.2.2 World-start confirmation is a read-only gate with a persisted last choice

The configured `level-name` is read raw and preserved. The inspector rejects empty, dot, traversal, absolute, and path-like names before using the value as one direct child of the server root. It rejects symlinks and non-directory targets, never follows directory symlinks, recognizes developed alternate saves using `level.dat` plus region/player data (including selected Forge dimension subtrees), and scans the configured world for size, newest regular-file mtime, region count, and playerdata count. Permission or walk errors result in `unavailable`, not an assumed empty/new world.

The summary is immutable data returned from a short-lived worker thread. The UI checks its generation and selected instance ID to discard stale results. Immediately before dispatching Start it re-checks that the server is still confirmed stopped and that `level-name` still matches the inspected folder; it repeats that check after the FML prompt. Only after `tmux.start()` succeeds does the UI persist `instance.extra["last_started_world"]` through the ordinary registry update. New/incomplete folders, changed selections, or older records with other developed saves require explicit confirmation. Other save folders are retained.

The watchdog uses the same inspection helper but cannot show a modal confirmation during an automatic restart. It therefore refuses the restart whenever the selection is unsafe/unavailable or `requires_confirmation` is true. Keep the inspection pure/read-only and separate from the lifecycle action that follows it.

**There is no single effective-properties reader today:** `PropertiesDoc.loads()` is an order/comment-preserving editor model which recognizes only literal `=` separators, trims key/value edges, and preserves simple duplicate lines; it does not implement the complete Java `Properties.load()` grammar. `ServerInstance.world_level_name()` separately recognizes only a stripped line beginning exactly `level-name=`, and `ServerInstance.server_port()` separately scans `server-port=` with last-key-wins behavior. Both return their ordinary defaults (`world` and `25565`) if `read_text()` raises `OSError`; the former also follows a symlink. `pack_update._configured_level_name()` uses a different, more Java-properties-like logical-line parser with escape/separator handling, but returns `world` on read failure too. Therefore UI/CLI start inspection, world convenience paths, port collision checks, and pack-update preserve planning can interpret the same bytes differently. A Rust port must not merge these into a new parser without golden cross-fixtures and an explicit compatibility decision. For safety-critical reads, return `MissingUseDefault`, `Value(raw)`, or `Unavailable(reason)` rather than treating unreadable input as the missing-file default.

**World-selection error distinction still needs tightening:** `ServerInstance.world_level_name()` checks `server.properties` with `Path.exists()`, reads it when present, catches `OSError`, and returns the default string `"world"` both when the file is absent and when it exists but cannot be read. `inspect_instance_world_start()` consumes only this string, so it cannot distinguish a legitimate missing-file default from an unreadable configuration; a symlinked `server.properties` is also followed by the current read. Before a Rust port, preserve legacy defaulting only for a genuinely absent regular config file. A present but unreadable, non-regular, or symlinked `server.properties` should produce an explicit unavailable/unsafe result and block Start/watchdog restart. Introduce a typed `WorldSelectionRead` (`MissingUseDefault`, `Value(raw)`, `Unavailable(reason)`) rather than returning a string that silently loses the I/O failure. Add fixtures for absent file, regular file with no `level-name`, permission/read failure, symlinked file, broken symlink, malformed/empty value, and a valid custom world name.

**World-scan cost:** when a selected world folder exists, `inspect_world_start_state()` recursively walks it and stats every regular file to calculate total bytes, newest mtime, region count, and playerdata count. The pre-start summary worker runs when an instance is selected and is run again afresh when Start is pressed; WorldTab may separately run `ServerInstance.world_size_bytes()` when that tab is opened. The work is off the Qt event loop, but Start still waits for the full traversal to finish, and very large GTNH trees can contain many thousands of region files. This is not a measured latency claim. Benchmark by file count and tree shape. A candidate design is to separate a fast safety classification (safe selected path, selected save state, alternate developed saves, confirmation requirement) from optional detailed size/mtime/count statistics, or to reuse a versioned read-only inventory only after action-time revalidation. Do not let a partial/failed safety scan become "new" or "no other worlds"; if any required path cannot be inspected, return unavailable and block the action.

### 3.2.3 Watchdog polling and the multi-instance scaling gap

The active watchdog timer runs every 10 seconds, but the current code performs fresh tmux client calls inside the watched-instance loop: normal running instances use one `has-session` subprocess and one `list-panes` subprocess each. The `watchdog.py` module comment says one `list-sessions` call covers all watched instances, but that batch query is not used by the current `_poll()` implementation. This is a mismatch between the module comment and implementation.

A candidate refactor is a single per-tick session list and a global pane snapshot, with per-instance observations derived from the exact registered tmux session names. The pane snapshot must preserve the current exact-session/current-window/first-pane result. It must not choose an arbitrary pane or silently substitute the active pane without proving equivalence. The tmux manual supports `list-panes -a -F` and the required session/window/pane format fields, but the implementation still needs compatibility tests against the installed tmux versions Crucible supports. See the detailed benchmark and command design in the performance audit.

Preserve the active-only timer and all fail-closed semantics: two misses before crash classification, unknown session or pane is not a miss, a GTNH wrapper with Java absent is different from Java foreground, a requested Stop stays disarmed, and world-start confirmation still gates automatic restarts. Existing tests establish these semantics for one watched instance but do not test multi-instance query counts, multiple active windows, or multiple panes.

### 3.3 Fleet backup

BackupTab and WorldTab dispatch to FleetBackupManager in workers. The manager serializes backup/world/update operations with a global operation lock, snapshots the full registered fleet, checks process status/readiness, flushes running worlds, stages immutable generations, verifies, publishes by atomic rename/fsync, rotates retention only after successful publication, and defers source cleanup until retained generations are safe.

Incremental behavior is already significant: unchanged content can be hard-linked from the preceding immutable generation, avoiding fresh reads/writes. Do not replace this with an always-full copy or an archive format change under the guise of a Rust port.

### 3.3.1 Fleet generation manifest and restore contract

The fleet backup's manifest is a versioned data contract, not just a file list. The current schema is version 1 and each generation stores one canonical JSON manifest at `manifest.json`.

**Top-level generation fields**
- `schema`: current integer generation schema (1).
- `status`: must be `complete` before a generation is considered publishable.
- `generation_id`: must match the generation directory name.
- `created_at_utc`: UTC timestamp with microsecond precision.
- `retention_generations`: two-generation retention declaration.
- `servers`, `file_count`, `logical_bytes`: inventory totals.
- `bytes_copied`, `bytes_reused`: storage-work accounting, not logical restore size.
- `instances`: per-server captured inventory.
- `legacy_sources`, `legacy_sources_excluded`: opaque external retired/manual source material carried into the generation, plus sources intentionally omitted as incomplete/failed-import data.
- `manifest_sha256`: SHA-256 of the canonical JSON encoding of all preceding manifest fields, with sorted keys and compact separators. This detects accidental/tampered-field changes when the digest is not also rewritten, but is an unkeyed checksum, not an authenticity signature.

**Per-instance fields**
- Identity/context: `id`, `name`, resolved `path`, a registry snapshot (`registry`), pack `version`, Minecraft version, loader/version and tmux session.
- Capture context: `capture_status` (`stopped` or `running (save-off/save-all/save-on)`), `active_world`, and `world_saves` (world name, active flag and `level.dat` byte count).
- File tree: `directories` (relative path and original mode), `files` (one record per regular file), `excluded` (path and explicit reason), and `excluded_roots` (top-level subset of exclusions).
- Migration compatibility: `legacy_world_archives` (immutable copies of old world ZIPs with slot/time metadata and hashes) and `legacy_archive_excluded` (e.g. symlinks/partial archives).

Each normal file record includes `path` (safe relative POSIX path), `size`, SHA-256, original mode, `source_stat` (device, inode, size, mtime_ns, ctime_ns), and `reused_from_previous`. Directory records include relative path and mode. Legacy archive records add filename, slot name and created time; legacy-source records include the original source-relative path, source type, per-file source path/snapshot path/hash/stat/size, file count, byte total, and skipped-entry reasons.

**Publication and verification behavior**
- The current server walk excludes a documented set of cache/log/temp/session files and directories. Every excluded path is recorded with a reason; symlinks and non-regular filesystem objects are explicitly excluded, not followed.
- For live server files, Crucible opens the source with `O_NOFOLLOW`, records `fstat` before/after, streams 1 MiB blocks while hashing, checks the byte count, fsyncs a unique temporary copy, and publishes with `os.replace()`. It then reads a fresh destination copy again and compares SHA-256. After all files, it repeats the structural inventory and checks final source stat signatures to catch files changed later in the long walk. `O_NOFOLLOW` applies to the final file component only: `_copy_and_hash_live()` still opens the complete source pathname rather than walking from pinned parent-directory file descriptors with `openat`/`openat2`. The earlier `os.walk()` rejects directory symlinks and the final inventory/stat pass catches many parent swaps or edits, but those are separate pathname traversals, not a descriptor-anchored proof that every component remained the same object between enumeration and open. This is best described as strong mutation detection with a residual same-user path-replacement race, not a fully race-free no-follow tree walk. A hardened future adapter should traverse each component relative to an already-open directory descriptor with `O_DIRECTORY|O_NOFOLLOW` (or a Linux `openat2` policy such as `RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS`), retain directory identity, and fail if a component changes. Do not add this complexity without a targeted race harness and benchmark.
- Unchanged files are hard-linked only from a prior immutable generation after source-stat signature match, expected-size match and a check that the previous snapshot is read-only. If hard links are unavailable, it copies and verifies the previous immutable file. It never hard-links a live world file into the snapshot.
- The manifest hash is verified on every `_load_manifest()`. `verify_generation(deep=False)` checks manifest checksum/schema/status/directory ID, file/directory existence, relative paths, sizes, read-only modes, inventory counts and logical bytes, but it does **not** hash every payload file. `verify_generation(deep=True)` additionally reads and SHA-256 hashes every file. Server restore defaults to deep verification; the UI restore worker passes `deep_verify=True`. Shallow verification is for listing/fast inventory, not permission to restore unverified payload.
- A generation is staged, its files/directories sealed read-only, manifest and directories fsynced, shallow-verified, atomically renamed to its final generation ID, then final generation/root directories are fsynced strictly. A post-rename durability failure rolls the unpublished generation back before pruning. Existing invalid generations block another publish/retention rotation rather than being silently discarded.
- Restore writes to a new isolated directory only; it refuses an existing target, symlinked parent components and targets inside/over any registered server path. Files are copied, original modes restored, and by default each restored file is re-hashed before the staging root is renamed into the new target. Older named world ZIPs are restored into a separate hidden recovery directory, not injected into the live world save.

**Limits and performance questions**
- The manifest is read and JSON-decoded as one whole file in `_load_manifest()`; there is no explicit manifest-byte or entry-count cap. A legitimate server with a very large tree can therefore produce a very large JSON allocation at generation listing/verification time. Measure manifest bytes, decode time, peak RSS and file count with many-small-files fixtures before introducing a cap. A safe cap must be compatible with real Crucible/GTNH installs, or move to a versioned sharded manifest/index while keeping one complete generation inventory.
- Deep verification intentionally performs a full read of every payload; it is required by the default restore path today. Do not substitute shallow metadata verification without an explicit recovery-policy decision and tests.
- The manifest SHA-256 is not a signature: a local actor able to rewrite both manifest and digest can create a self-consistent false manifest. Snapshot integrity therefore depends on private directory permissions, immutable generations, SHA-256 payload checks, and verified publication, not on provenance/authenticity against a privileged local attacker.

The fleet-backup suite already covers stopped snapshot/deep verify/restore, hard-link reuse only from a prior immutable generation, exact two-generation retention, failure preserving the prior generations, directory-fsync and post-rename-fsync failures, unready/running server save acknowledgement, unknown/unmanaged refusal, symlink/exclusion behavior, invalid-manifest retention, immutable modes, isolated restore targets, legacy archive migration and two-generation source retirement. Remaining fixture needs include giant manifest memory/parse profiles, truncated/oversized manifest reads, duplicate/extra manifest fields, parent-directory symlink replacement between enumeration and open, root/parent directory inode replacement during long copy, and a deep-vs-shallow corruption matrix proving that shallow listing may pass while deep restore blocks.


### 3.3.2 Legacy world ZIPs and BackupManager compatibility path

The legacy per-instance archive manager remains in the product for old named world ZIPs and validated world swaps. It is not the fleet retention authority, but its persistence and restore paths still handle user-owned world data.

**Backup-root identity and privacy**
- BackupManager constructs BASE_DIR / instance.id directly, with current BASE_DIR at ~/.local/share/crucible-backups, then calls mkdir(parents=True, exist_ok=True). Unlike the fleet manager's SHA-256 server-key directory component, this does not validate or encode the raw registry ID as one safe path segment. Registry loading currently accepts a supplied ID without path-segment validation, so a manually edited/corrupt ID containing slash, dot-dot, or an absolute path can redirect legacy backup listing/writes outside the backup root. Do not hash legacy IDs as an unannounced migration because old files are stored under the raw ID; validate existing IDs as a single safe segment before use and provide a separate explicit migration if changing the storage key is ever required.
- The legacy constructor does not set or verify owner-private permissions on BASE_DIR or the per-instance directory. A new directory receives ambient umask-derived mode; an existing directory is left as-is. ZIPs contain full world data. The fleet manager explicitly restricts root/generation/staging directories to 0700; the legacy compatibility path does not have an equivalent privacy guarantee.
- list_backups() uses glob("*.zip") and Path.stat(), which follows archive symlinks. Slot sidecars are read by normal path open without size/schema/symlink checks. A symlinked archive can therefore be listed as if it were an ordinary backup file; a later restore follows the archive path unless an expected fleet hash is actually enforced.

**Legacy ZIP creation and slot metadata**
- create_backup() is explicitly documented as a legacy compatibility API, not the normal UI/CLI capture route. It enumerates selected world folders, builds an in-memory file list, writes a deterministic sibling .zip.partial with ZipFile(..., "w"), reopens it, calls testzip() and requires a non-empty level.dat, then renames it to the final ZIP. It has no explicit member-count, total expanded-byte, per-file-size or compression-ratio policy at creation time; traversal follows the helper's resolved world paths and skips symlinked files.
- The .zip.partial is a predictable path opened in write mode rather than an exclusive/no-follow temporary file. A pre-existing symlink or colliding path can be followed/truncated before the final archive is published. Its failure cleanup unlinks the partial path but is not rooted in a directory descriptor.
- Named-slot metadata is a sidecar {archive}.zip.json. _write_slot_metadata() uses a predictable .tmp path and ordinary write_text()+replace, with no no-follow/exclusive temp, fsync, size bound, or schema version. Its writer errors are swallowed after a ZIP backup has succeeded; label loss is treated as non-fatal. Preserve backward compatibility for old unnamed ZIPs, but do not treat a sidecar parse as a verified archive.

**Restore validation and a dormant integrity helper**
- _validated_backup_members() materializes the full ZIP central directory with infolist(), then caps it at 2,000,000 entries. _backup_level_name() is called before that validation and independently materializes namelist() with no entry cap. Thus the count cap applies only after the central directory has already been parsed/allocated, and there is no separate central-directory byte/memory bound.
- Member validation rejects NUL/backslash/absolute/traversal paths, unapproved top-level world/dimension folders, symlinks/special files and duplicate normalized names; it sums expanded bytes and checks available disk space while preserving at least max(512 MiB, 5% of free space). There is no per-member size or compression-ratio cap. A very high-ratio archive can consume CPU even when aggregate expanded size fits the free-space check.
- Extraction streams 1 MiB chunks into the new world target and checks that each member produces exactly its declared uncompressed size; reading through EOF also lets zipfile validate CRC. Post-swap verification checks non-empty level.dat and that dimension directories named in the archive exist. It does not hash every extracted file against a per-member SHA-256 manifest. A CRC is not a cryptographic integrity guarantee.
- A fleet-backed BackupEntry carries an expected sha256, and BackupManager._verify_fleet_archive_hash() exists with O_NOFOLLOW descriptor handling, but a source-wide call-site search finds only its definition. Neither _validate_backup_archive(), _extract_validated_backup(), nor swap_world() invokes it. Therefore a temporary ZIP exported from a fleet generation is deep-verified when created, but the helper's stored expected archive SHA is not rechecked by BackupManager immediately before/during world restore. The existing test named test_fleet_backed_world_archive_must_match_manifest_sha256 calls _verify_fleet_archive_hash() directly and proves that helper works in isolation; it does not exercise swap_world() or _validate_backup_archive(). Add an end-to-end test that mutates/replaces a fleet-exported ZIP after its expected hash is attached and proves the actual swap path rejects it before renaming the live world. Add an extraction destination-parent symlink swap fixture and inject a target-cleanup failure to prove the original world remains recoverable and the error names the preserved path.
- Extraction writes directly into the target world root after the current world was renamed aside. Each member is written with `destination.open("wb")` after a separate path-resolution/containment validation pass; the extraction does not hold a no-follow directory handle, use `openat`-style relative creation, stage each file, or extract the complete world into a private sibling directory before publication. An external process can replace a validated parent with a symlink between validation and open. The archive itself cannot supply that symlink because symlink/special members are rejected, but the path-based sequence is not race-free against concurrent local mutation. The world operation worker has a fleet-generation prebackup and holds the global operation lock; on ordinary extraction/verification failure, the new target is removed and the previous world directory is renamed back. The exception path calls `shutil.rmtree(target_world_root, ignore_errors=True)` and then attempts the old-world rename without checking that the partial target was actually removed. If cleanup fails, the rollback rename can fail because the target still exists, leaving the old world in its `.pre-swap-*` folder. This is a valuable normal-path recovery flow, but it depends on the caller contract and old-folder rename; the lower-level BackupManager methods do not acquire the fleet lock or independently verify that the server is stopped.
- _write_level_name() checks the properties path and a fixed .crucible-tmp sibling for symlinks/existence, then writes and replaces using ordinary path operations. It does not use exclusive tempfile creation, file fsync, directory fsync, or a directory descriptor, so the precheck/write sequence is raceable and atomic rename is not a full power-loss durability guarantee.
- prune_pre_swap_dirs() uses shutil.rmtree(candidate, ignore_errors=True) and increments its deleted count regardless of whether deletion succeeded. Its helper itself does not acquire the global fleet lock; the visible Worlds tab cleanup action directly calls it rather than using the checkpointed worker branch, as noted in the operation-lock audit.

**World reset/wipe caller contract**
- reset_world() trusts the caller's safety_backup_verified=True and non-empty fleet_generation_id flags; it does not independently open the generation manifest or prove that ID exists/contains this instance. Production WorldTab supplies those values after taking a fleet snapshot under the global operation lock, but direct callers/tests can supply any truthy ID.
- wipe_world() similarly checks only the boolean and a non-empty generation ID before shutil.rmtree(world_root); the production worker is the thing that actually created/verified the fleet generation and checked stopped state. The lower-level API is not self-authorizing.
- Reset renames the old world aside and attempts to restore the path if updating level-name fails; if automatic rollback also fails it reports the preserved path and tells the owner not to start. Wipe is intentionally permanent after the caller's fleet checkpoint, so it has no local rename-aside recovery.

The migration boundary must preserve the distinction between the production transaction owner (WorldTab worker + fleet operation lock + verified generation) and legacy BackupManager's lower-level callable APIs. Before any Rust restore/extraction code is connected, add tests for raw-ID path traversal, directory permissions, symlinked archive listing, partial/tmp symlink, oversized central directory before count check, high compression ratio, fleet archive SHA mismatch, extraction CRC/truncation failure, post-swap content corruption, destination parent symlink replacement between validation/open, failed partial-target cleanup during rollback, _write_level_name temp collision, prune reporting when rmtree fails, and reset/wipe refusal when the supplied generation ID does not exist or does not contain this instance. Keep old ZIP reading compatible; do not silently rewrite or re-home existing archive folders.


### 3.4 Import and pack update

Import paths detect source type and build a plan, extract archives into staging on the destination filesystem when possible, reject unsafe paths/links/oversized entries, copy server-safe content, add metadata/receipt, optionally download indexed mods and install server software, and surface warnings. GTNH pack updates first create a reviewable plan, then separately stage/download/apply, preserve world/config/mod inputs, verify, and keep rollback. Apply is serialized with fleet backups in both GUI and CLI. Rollback and previous-install prune are not serialized by their current GUI/CLI callers, even though rollback renames the live tree; a backup or competing rollback can race those effects. See the operation-lock call-site audit in section 2.5.2.

`plan_update()`'s docstring currently says it "Never touches the filesystem", but the implementation does: server-root existence, raw/effective `level-name`, top-level world inventory, preserve-directory/file existence, local archive checks, `shutil.disk_usage()`, and recursive `_dir_size()` are all filesystem reads. Two inventory helpers currently erase incomplete-scan information:

- `_world_names()` returns the already-selected configured-world list when `root.iterdir()` raises. During alternate-save discovery, `child.is_dir()` and `level_dat.is_file()` are best-effort boolean checks; inaccessible entries are skipped as though they were not worlds. The returned list can be partial without an error status.
- `_dir_size()` catches an `OSError` from `rglob()` and returns the bytes seen so far; per-file stat errors are also skipped. `plan_update()` uses that result to calculate `2 * current_size + minimum_free_space`, so a partial scan can understate stage/swap disk needs.

The effect path has safeguards: `apply_update()` requires a verified fleet checkpoint before download/staging, validates each preserve tree for symlinks/special files, and rechecks tmux/port immediately before live rename. But the checkpoint is a recovery route, not proof that the plan preserved every world in the resulting install. `_copy_preserved()` also skips a preserve-list entry when `src.exists()` is false; it does not prove that a previously inventoried owner path remained present and readable. On an actual copy error it fails before rename, leaving the live install in place.

Required future design: `WorldPreserveInventory { entries, complete, errors }` and `TreeSizeEstimate { bytes, complete, errors, capped }`. Any inability to enumerate the server root, identify the selected world, inspect a candidate world marker, or stat a required file must set `complete=false`. Planning must block or request owner review; it must not emit a "preserve all worlds" plan from partial evidence. Disk planning should fail closed when the size estimate is incomplete or use a clearly defined conservative upper bound. Apply should compare the current preserve inventory against the reviewed snapshot before staging and fail if required items disappeared/changed; it must not silently omit entries. Rollback with `keep_current_world` must make the same complete-inventory check before renaming anything. Add permission-failure fixtures, a disappearing `level.dat`/world between plan and apply, and partial `rglob`/stat failure. Keep the fleet generation as the recovery source; do not replace it with per-world best-effort copies.

The extraction path intentionally uses the destination parent as the temp directory so a multi-GiB pack is not expanded under a small tmpfs `/tmp` and a second cross-device copy can be avoided. This is a performance feature worth preserving.



### 3.4.1 Pack-update planning needs complete filesystem inventories

The current `plan_update()` docstring says it "Never touches the filesystem", but the implementation performs reads of the server root, configured properties, top-level world inventory, preserve directories/files, local archives and disk usage, including recursive `_dir_size()` work.

The present inventory APIs are not complete/partial aware:
- `_world_names()` returns the selected-world list if `root.iterdir()` raises, and silently skips some inaccessible alternate-world markers. It can return a partial preserve list without an error.
- `_dir_size()` catches recursive-walk errors and per-file stat errors, then returns a partial byte count. That partial result feeds the update disk estimate.

This means an unreadable tree can omit alternate owner worlds from the new install or understate temporary disk needs. The mandatory fleet generation remains a recovery point, but it is not equivalent to preserving all worlds in the new live installation. `_copy_preserved()` also continues when a planned source path appears absent at apply time; a complete inventory must be rechecked against the reviewed plan before staging and must not quietly drop required entries. Rollback's `keep_current_world` uses the same world-name helper, so incomplete discovery can limit which worlds it carries over (the entire prior live tree remains set aside).

Future boundary: `WorldPreserveInventory { entries, complete, errors }` plus `TreeSizeEstimate { bytes, complete, errors, capped }`. Incomplete server-root/world/disk scans must block planning or require explicit owner resolution. Apply and rollback must compare current inventory to the plan before rename. Add permission-denied `iterdir`, unreadable `level.dat`, partial `rglob`/stat, removed-world-between-plan-and-apply, and disk-estimate-incomplete fixtures. The plan's current docstring should eventually be corrected because the function is filesystem-reading, albeit non-mutating.

### 3.5 CLI invocation and compatibility flow

The CLI entry is `crucible.__main__:main`. Its observed order is:

1. Build the `argparse` parser and parse argv. Argparse handles `--help` before Crucible loads the registry or initializes any UI.
2. With no subcommand, print the banner and root help, then exit with code 0.
3. For normal commands, print the banner. `gui` and hidden `shortcut-action` suppress it.
4. Construct `InstanceManager`, call `load()`, construct `TmuxManager`, then dispatch by exact command string.
5. Each handler owns its output and uses `sys.exit(1)` or `sys.exit(2)` for failure classes in different paths; successful handlers often return `None`. The exit-code convention is not currently centralized in a typed result.

Start is a special behavior contract: `_confirm_cli_world_start()` rejects unsafe/unavailable summaries, requires a TTY for confirmation, and requires the owner to type the exact word `START`. Non-interactive invocations cannot bypass confirmation. The dispatcher does not duplicate the GUI, but it still calls the same shared TmuxManager/domain routines.

Worlds-tab cleanup has a source/UX mismatch worth preserving in the audit: the visible `Clean up old world copies` button invokes `_cleanup_pre_swap_dirs()` directly, synchronously calling `BackupManager.prune_pre_swap_dirs()` without the lock or fleet checkpoint. `_WorldOperationWorker` contains a separate locked/checkpointed `cleanup` branch, but no production call site routes the visible button through `_start_fleet_action("cleanup")`. Do not treat the presence of that worker branch as proof that the visible mutation path is protected.

A Rust CLI replacement should not be the first Rust integration slice. Before even prototyping it, capture golden invocations for every command family, all aliases/options and their defaults, stdout/stderr, exit status, whether the command touches the registry, filesystem/network/processes, TTY behavior, and environment/working-directory assumptions. The current CLI is a public compatibility surface and also a useful Python reference path while the GUI remains Python.

### 3.6 Client export and share

The client export pipeline may read the same JAR/config inputs multiple times for different guarantees: metadata inspection, source fingerprinting, distribution SHA-256 review, archive creation, sealed-member hashing/privacy inspection, archive SHA-256 and final source/catalog revalidation. This is expensive by design in places because the exported bytes must match the bytes reviewed and the input set must remain stable.

**Source-confirmed stages and guarantees:**
- `_enabled_mods()` and `ModManager.inspect_jar()` classify installed top-level mods by metadata/side; server-only side and conservative filename/ID hints are excluded. Exact matching bytes from the selected Prism client source confirm client use for unknown-side server JARs; profile-exclusive client/unknown/both JARs can be included, but that is not distribution permission. Duplicate bundled mod IDs fail the export.
- The optional matching Prism source must be a real installed profile, with exact Minecraft version and exact loader/version agreement. The exporter preserves launcher components, patch JSON and profile-local libraries, which is needed for modern GTNH/LWJGL3ify. Prism profile client-only files and resourcepacks have separate inclusion policies; resourcepacks are off by default and opt-in.
- Server config is authoritative when server and client profile paths conflict. KubeJS export is restricted to `client_scripts/`, `startup_scripts/`, `assets/`, and `config/`; server scripts and generated data are excluded. `defaultconfigs/`, worlds, screenshots, logs, options and servers lists are not copied as ordinary client config.
- The curated distribution catalog is strict JSON, bounded and revision-hashed. Records are keyed by the exact JAR SHA-256 and include decision, evidence URL, project URL, review date, basis, license/conditions, alternative download and curator notes. `permitted` records require a license identifier/URL or an explicit-permission basis. Duplicate hashes, malformed fields, unsafe URLs, invalid dates and future review dates fail catalog loading. `unverified` does not mean permission: that exact JAR is still included with an explicit warning. `conditional` carries the conditions into review. `prohibited` JARs are excluded and require a reviewed alternative-download URL plus a manual-install instruction; if no alternative exists, export stops before a ZIP is written.
- Before archive publication, the exporter reads and hashes every payload member, rejects duplicate/unsafe member names, records path/size/SHA-256, scans the configured text subset for privacy patterns, and embeds `crucible-manifest.json`. ZIP members are read through EOF (including CRC validation); the archive SHA-256 covers the whole final archive, including the embedded manifest. Every bundled JAR's sealed payload digest is compared with the earlier distribution-review digest. Catalog revision is checked again before final publication.
- Privacy scanning is bounded, not comprehensive: supported config/KubeJS text files are scanned up to 8 MiB per file and 256 MiB aggregate, with findings capped at 50. Nested config ZIP scanning accepts nested archives up to 64 MiB. Known binary assets are skipped; unsupported file types, binary-looking text candidates, size-limit skips, nested-read failures and findings truncation are reported. The manifest's `privacyReview.coverageComplete` is false when any of those coverage gaps occur. A build can still return `ExportResult.ok=True` with incomplete privacy coverage or unresolved unverified/conditional distribution warnings; this is intentional because those cases are surfaced for owner review rather than described as a clean result. The UI's separate approval gate must stay attached to these warnings.
- The share workflow uses Prism ZIP only. `_PrepareWorker` computes a deterministic content fingerprint before searching the cache/build; the fingerprint includes server/client roots (only inside the opaque hash), selected options, catalog revision, relative paths and SHA-256 of relevant inputs. Files are checked for stable stat identity before/after hashing. Export rechecks the same fingerprint and catalog revision before publication. The upload worker recomputes it again immediately before network activity. A change or unavailable input blocks upload and requires rebuild/review.
- The generic `ClientExportDialog` also supports MRPACK and CurseForge formats. Those non-Prism `export()` calls do not currently compute `input_fingerprint` or re-fingerprint source files at the end; exact bundled JARs are still checked against their distribution-review digests, and the generated ZIP is internally sealed, but there is no equivalent whole-input snapshot guarantee for concurrently changing config trees. This difference is important: the public Gofile workflow is Prism-only today, so its stronger fingerprint guard is not automatically a property of every export format.
- Local player ZIPs are stored in a private `player-packs/` directory (0700); names are reserved with `O_EXCL` and files are set to 0600. Cache sidecars are bounded, atomically written 0600 metadata; reuse requires a matching source fingerprint, archive SHA-256, full ZIP member/payload hash verification, a valid embedded manifest and a current distribution-catalog review. A failed permission hardening removes a newly built unprotected ZIP where possible and blocks upload.
- The UI requires three independent acknowledgements (file/privacy review, distribution/license conditions, public-link awareness) before upload is enabled. Changing the source path or resourcepack option invalidates the review and clears approvals. The upload worker revalidates underlying server/Prism inputs; the Gofile adapter independently validates the local ZIP bytes.
- `gofile.upload_file()` refuses symlink/non-regular local files; opens with no-follow where supported; compares `lstat` and `fstat`; hashes the opened file descriptor; checks it against the reviewed archive SHA; seeks and streams the same descriptor in 256 KiB network chunks while computing a second SHA-256 and MD5; verifies byte count and file identity again; and checks cancellation before sending the final multipart boundary. The endpoint is fixed to `upload.gofile.io` over TLS. Owner token is optional, sent only as an Authorization header and never persisted; guest credentials in provider response are discarded.
- The returned Gofile page URL must match the exact HTTPS host/path form `gofile.io/d/<id>` or `www.gofile.io/d/<id>`, with no userinfo, query, fragment or non-default port. File ID/name are bounded. If remote size or MD5 fields are present, malformed/mismatched values reject the result. Those fields are optional; when absent the result explicitly sets `size_verified`/`md5_verified` false. Crucially, Crucible does not independently re-fetch the public download page or download the remote file, so a returned link is provider-confirmed/shape-validated, not independently verified as retrievable. Cancellation/network ambiguity after transmission can leave an unconfirmed remote copy that Crucible cannot retract.
- Share history is local and bounded to 50 allowlisted events, with a 1 MiB file cap, owner-private parent/file permissions (0700/0600), atomic writes, sanitized fields and validated Gofile URL shape. It records local path, archive hash, input fingerprint, server name, size, provider, last-returned link, verification flags and generic error category; provider tokens, headers, raw exceptions and response bodies are excluded. Clearing history does not remove ZIPs or revoke public links.

This is a benchmark candidate, not an invitation to drop checks. Future optimization could consider a verified staged input snapshot with a single digest inventory reused by review and build, but only if it still detects source changes and ties every catalog decision to the exact bytes embedded in the ZIP. Include adversarial mutation, privacy-scan incompleteness, catalog mutation, and duplicate/unknown JAR cases in parity tests.

## 5. Benchmark and profiling discipline

The current CI runs tests on Python 3.11 and 3.13 on Ubuntu 24.04, an offscreen Qt smoke run, and UI preview capture. It does not currently build or test Rust and does not run a performance benchmark suite.

Use profiling/benchmark tooling compatible with the existing Python matrix:

- `python -X importtime` for import self-time/cumulative-time analysis. Python documents that it is available from Python 3.7; its multi-threaded output can be misleading, so use it for controlled cold-import runs.
- `cProfile` for deterministic call counts and CPU attribution on Python 3.11/3.13. Do not treat profiler output as benchmark timing.
- `time.perf_counter_ns()` or `timeit` for repeated timing of isolated functions; for end-to-end workflows capture wall time, CPU time, bytes read/written, peak RSS and subprocess count.
- Native Linux tools such as `perf stat` / `perf record` for syscall, CPU and I/O attribution, where permissions and kernel configuration allow.
- When Rust is introduced, use release builds for runtime comparisons, `cargo bench`/Criterion-style harnesses for isolated CPU code, and a native profiler for hot-path attribution. Keep debug symbols in benchmark builds. Record compile/link time and binary size as separate product costs.

Do not compare Python debug execution to optimized Rust release binaries. Do not compare warm-cache runs with cold-cache runs. Repeat on the same filesystem and device. Record p50/p95, not only the best single result. Measure total workflow latency, including FFI/IPC, serialization, input hashing, UI handoff and disk flushes.

## 7. Packaging and release constraints

The installed layout is important to the Rust integration choice. Current install.sh behavior:

- Candidate interpreter order is Python 3.13, 3.12, 3.11, then python3; a valid CRUCIBLE_PYTHON override is honored. It prefers an interpreter that already imports PyQt6.
- Creates a per-user venv with --system-site-packages. If Qt is not already visible, Nobara/Fedora gets a dnf package attempt; otherwise PyQt6 is installed with pip inside the venv.
- Copies distributable source into $APP_ROOT/source, excluding Git metadata, caches, build output and previous venvs.
- Runs compileall, imports PyQt6 and Crucible, checks the package version, and invokes crucible --help before publishing.
- The launcher resolves its own symlink with readlink -f, derives the real app root, prepends $APP_ROOT/source to PYTHONPATH, and execs $APP_ROOT/venv/bin/python -m crucible.
- Existing app directory is renamed to a .crucible-previous.* rollback path. Staged app is atomically renamed into place; the final-path launcher is smoke-tested before the rollback copy is deleted. Desktop integration is written after publication.
- Backups live outside the app root; a legacy in-tree backup directory is copied with no-overwrite behavior. The installer creates BACKUP_HOME with ordinary mkdir -p and does not chmod/verify owner-private permissions; the legacy BackupManager stores ZIPs directly beneath this parent. A fresh default-umask install can therefore leave the shared backup root and legacy archives group/world-readable, unlike the fleet generation subtree's explicit restrictive modes. The installer and legacy manager should enforce a private 0700 root and private files without silently broadening permissions on unrelated parent directories.
- The one-line installer queries GitHub's latest release, requires the exact Crucible-tag-source.zip and Crucible-tag-SHA256.txt asset names, bounds download sizes, verifies SHA-256, rejects unsafe ZIP paths/symlinks/oversized expansion, requires exactly one install.sh, tests ZIP CRCs, then invokes the installer.
- No Rust toolchain is currently required from the owner at installation time.

**Packaging trap for PyO3:** the launcher prepends the copied source tree to PYTHONPATH. Simply pip-installing a wheel into the venv may not make its extension visible, because crucible is imported from $APP_ROOT/source before site-packages. A production design must deliberately place the native module inside the imported package tree, install the complete project as a wheel and stop shadowing it with a source path, or define another explicit loader strategy. Do not assume "pip installed the wheel" means the imported crucible package can see its extension.\n\n**Installer backup-migration failure is currently fail-open:** when the previous app has an in-tree backups directory, install.sh runs `cp -a -n "$APP_HOME/backups/." "$BACKUP_HOME/" || true`, prints a success message regardless of the copy result, then eventually removes the OLD_APP rollback directory after the new install is published. A disk-full/permission/path failure can therefore leave some legacy backups uncopied and then delete the only old copy. The `-n` behavior also skips any existing destination without verifying that its bytes match the old source. Before any future Rust-related install-layout change, replace this with a checked, idempotent copy/verify/migrate step: for every source file, either prove the destination has identical bytes or copy and verify it; abort the upgrade or retain OLD_APP until all data is verified. Never swallow a backup migration error.\n\nThe new Rust CI workflow runs formatter, Rust tests, and Clippy on stable plus cargo tests on MSRV; it does not build a wheel/native library, upload a release artifact, or modify the current source ZIP. The recursive main tree contains no release-publishing workflow; the only existing main workflow is the Python test suite. The Rust crate and its fixtures are copied into the installed `source` directory by install.sh's broad tar command, but they are not compiled/imported or called. The future Rust artifact therefore needs an explicit release build/publish and installer stage; a green Rust CI job alone is not a deployable migration. The release source archive/checksum are manually/out-of-band assets relative to the workflows currently present in this repository.\n\nThe one-line downloader uses `curl --proto '=https'` on the API, source ZIP and checksum requests. Current curl documentation says `--proto` restricts protocols allowed for transfers and `--proto-redir` cannot override protocols denied by `--proto`; the default redirect list may include HTTP/FTP, but those are already denied by the current `=https` transfer allowlist. An explicit `--proto-redir '=https'` would make the redirect policy easier to audit, but this is defense-in-depth rather than a confirmed downgrade vulnerability. [curl current man page](https://curl.se/docs/manpage.html).\n

Therefore, any production Rust component must be delivered as a verified prebuilt artifact or compatible wheel. Do not make owners install Rust or compile the app during routine updates. The build pipeline must produce platform/Python-compatible artifacts, include and verify them, stage them with the app, test import from the final path, and restore the old installation if the artifact is missing or incompatible.

tests/test_release_scripts.py contains nine focused checks covering installer staging/rollback markers, interpreter selection (including CRUCIBLE_PYTHON), symlink-resolving launcher behavior, lazy tab data loading, CLI lifecycle wiring, exact verified release assets, and package data declarations. These tests use source checks/stubs; they do not execute a full upgrade, do not inject failure into legacy-backup copying, and do not verify post-install backup permissions or Rust artifact import. Add a temporary HOME integration test that creates old in-tree backups, simulates copy failure/destination collision, verifies the old copy is retained, checks owner-private mode, and runs the final launcher. Repeat after a Rust artifact is introduced.

If PyO3 is selected, measure wheel size/build matrix and Python 3.11/3.13 compatibility. PyO3's newest stable-ABI features and Python 3.15/free-threaded support are not a reason to raise Crucible's runtime requirement. If a JSON worker is selected, package a matching executable with the app and keep it long-lived, using batched meaningful work rather than paying process startup on every small status check.
